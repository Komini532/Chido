## 1. 全体設計思想

### 1.1 非同期・飛び入り参加前提

戦闘に「参加者募集」フェーズは存在しない。敵出現後、プレイヤーが最初に戦闘行為をした時点で `BattleSession` が生成され、進行中のセッションへの途中参加も常に許可される。

**戦闘はチャンネル単位で成立する。** 戦闘が行われるチャンネルは、戦闘チャンネル初期化コマンド（10.5参照）によってあらかじめ用意されている必要がある。1つのチャンネルに、同時に進行中の `BattleSession` は1つ以下である。

**プレイヤーは同時に複数の戦闘セッションへ参加できない（決定事項）**。他チャンネルで戦闘中のプレイヤーが戦闘行為を試みた場合、その旨のメッセージ（例: 「あなたは `<#チャンネルID>` で戦闘中です。」）を返してアプリ側で行動を拒否する。参加中セッションを保持するテーブルが1プレイヤー1行（`chido_player_in_battle_session`）である構造が、この制約の裏付けとなる。

**なぜこの制約を置くのか**: 非同期性は「他プレイヤーの行動を待たない」ことであって、「1人が複数の戦場に遍在できる」ことではない。同時参加を許すと、現在HP・TP・状態変化といった参加者ごとの状態が複数のセッションに分裂し、「プレイヤーのHPは1つ」という直感が崩れる。

### 1.2 1対1の「ターン」モデル

これが本システムの中核となる設計判断。

1回の戦闘行為（Attack/Skill/Defend/Use）は、「行動したプレイヤー」と「その対象1体」の間で完結する1対1の**ターン**として処理される。1回のターンは以下の流れで進行する。

1. 行動者が使用するスキルを確定する（プレイヤーのコマンド入力）
2. 対象（敵）が反撃に使うスキルを `action_pattern_type` に従って抽選・確定する（4.2参照）
3. 両者の確定したスキルの `Priority` と `Speed` から先攻・後攻を決定する（4.1参照）
4. 先攻側のスキルを再生する（複数モーション構成の場合は`motion_index`順に全モーションを再生、4.2参照）
5. 先攻の一撃で後攻が戦闘不能になった場合、ここでターンは終了する（後攻の行動はキャンセルされる、4.1参照）
6. そうでなければ、後攻側のスキルも同様に再生する
7. 両者のログをまとめて1回の応答として返す

プレイヤーが行動を起こすと、同一の呼び出し内でこの1〜7が完結し、対象からの反撃までを含めた結果が一度に返る。

**先攻・後攻の決定に、両者の選択スキルの確定が先行する（決定事項）**: 行動順は `Speed` だけでは決まらず、両者が実際に使うスキルの `Priority`（4.1参照）を参照する。したがって「対象の反撃スキルの抽選（ステップ2）」は「行動順の決定（ステップ3）」より前に済んでいる必要がある。この順序は 4.2 の敵スキル選択（`require_tp` フォールバックを含む）を先に確定させることで満たされる。

**このモデルを「ラウンド」ではなく「ターン」と呼ぶ理由**: ここでいう「ターン」は、あくまでこの1往復（先攻→後攻）の中だけで完結する単位である。戦闘全体で共有されるラウンド／フェーズ、イニシアティブ順、行動済みフラグ、座席番号によるターン制御は**意図的に持たない**。プレイヤーAのターンとプレイヤーBのターンは互いに独立しており、同期する必要がない。

**なぜこの形なのか**: Discord上で不特定多数のプレイヤーが不特定のタイミングで行動することを前提にすると、「全員の行動が揃うのを待つ」グローバルなターン進行は成立しない。各プレイヤーの行動を他者から独立した1往復のやり取りとして完結させることで、誰かの行動状況に関わらず、いつでも誰でも行動できる非同期性を実現している。

### 1.3 数値スケール（BigInteger）について

ステータス値が軒並み `BigInteger` なのは、**原型となったPython製のインフレ系ゲームからの名残**である。意図的な数値スケール設計の結果ではない。したがって「どこまで大きな数値を想定するか」という積極的なバランス方針は現時点では存在しない。

## 2. エンティティ

### 2.1 ステータス（`IEntity` / `EntityBase`）

| ステータス | 型 | 役割 |
|---|---|---|
| `MaxLife` / `CurrentLife` | `BigInteger` | 最大/現在HP。`CurrentLife` は `MaxLife` を超えうる（3.4参照） |
| `PAtk` / `PDef` | `BigInteger` | 物理攻撃力・防御力 |
| `MAtk` / `MDef` | `BigInteger` | 魔法攻撃力・防御力 |
| `Speed` | `int` | 行動順（詳細は4章）。算出式は2.3参照 |
| `Luck` | `Ratio` | アイテムドロップ率に影響（詳細は10.2参照）。算出式は2.3参照 |
| `Elements` | `[Flags] enum Element` | 本体属性。実効属性の算出は2.4参照 |

物理・魔法でATK/DEFを分離しているのは、後述のダメージ計算パイプラインで `AttackType` により参照する値を切り替えるため。

### 2.2 `Ratio` 構造体

割合を `permyriad`（10000 = 100%）の `int` で内部保持する専用の値型。`BigInteger` との乗算で `decimal` を経由すると精度が壊れるため、割合が絡む数値（ダメージ倍率・ドロップ率・属性補正・クリティカル倍率など）はすべてこの型で統一して扱う。

**DB側の格納スケールも permyriad に統一する（決定事項）**。ただし2つの例外がある。

| 例外 | スケール | 理由 |
|---|---|---|
| `_shape` サフィックスの列（敵マスタの種族値相当の値） | 100 = 1.00 | 手動でのバランス調整に馴染む。`Ratio` には変換しない |
| `power`（スキルモーション・スリップダメージの威力） | 整数% | 計算に使われる値であると同時にプレイヤーへの表示情報でもあり、意図的に小数精度を持たせない |

DB側の命名規約（`_shape` / `_rate` / `_bonus_rate` / `_bonus` / `power` / `weight`）の詳細は `chido-database-design.md` の「割合値のスケールと命名規約」を参照。

### 2.3 ステータス計算式（決定事項）

プレイヤー・敵は共通の計算式に従うが、一部の値の幅（Shape・強さ倍率・Speedの基本値）が異なる。

**レベルの導出（決定事項）**: プレイヤーのレベルは経験値から導出する。敵のレベルは累積敵レベル（10.1参照）から直接与えられる。

```
level = max(1, floor(√exp))
```

- **常にこの式で導出する**。`floor` は BigInteger の整数平方根であり、`√exp` を計算するために `Math.Sqrt`（浮動小数点）を経由してはならない。6.2 が「按分計算全体が有理数演算として閉じ、浮動小数点が一切混入しない」ことを設計価値としているのと同じ理由で、レベル算出も浮動小数点を通さない。整数平方根は**ニュートン法**で実装する（初期値をビット長から概算し、`x_{n+1} = (x_n + exp / x_n) / 2` を単調非増加になるまで反復して床値に収束させる）。
- **クランプ（下限1）は `Level` プロパティの取得時点で行う**。表示（`/status` 等）・計算の双方が同一の導出関数を通るため、あらゆる読み出しで異常値が遮断される。
- **初期値との関係**: 新規プレイヤーの経験値は `exp = 1` で初期化される（アプリ側の定数として `INSERT` 時に書き込む。10.4 の「草原」固定と同じ前例に倣い、DBのデフォルト値には委ねない）。正規のプレイヤーは常に `exp ≥ 1` が保証されるため `floor(√exp) ≥ 1` となり、上記クランプは理論上発火しない。したがってクランプは「初期値保証」ではなく「`exp = 0` 等の想定外値が万一入った場合のフェイルセーフ」である。初期値保証（`exp = 1`）とクランプ（下限1）は冗長ではなく、正常系を初期値で・異常系をクランプで塞ぐ**二重の防御**である。両者は同一の定数（1）を参照し、独立に持たない（一方だけ変えて不整合が出ることを防ぐ）。

**基礎ステータス**（HP・物理/魔法攻撃力・物理/魔法防御力に適用）:

```
基礎ステータス = レベル × Scale(ステータス区分) × Shape(ステータス区分)
```

- `Scale(ステータス区分)`: HPは12、攻撃力・防御力は8。
- `Shape(ステータス区分)`: ポケモンでいう種族値に相当する、正規化されたステータス倍率。プレイヤーはすべて1.00固定、敵は個別設定（`chido_enemy_master` の `hp_shape` / `patk_shape` / `pdef_shape` / `matk_shape` / `mdef_shape` 列がこのShapeに相当する）。

**戦闘時ステータス**（実際の戦闘で参照される値）:

```
戦闘時ステータス = 基礎ステータス × 強さ倍率 × 装備補正(+%) × 状態変化補正(+%)
```

- `強さ倍率`: プレイヤーは1固定。敵は個別設定（`chido_enemy_master.strength_rate`。例: ボスとして出現した敵には2などの高い倍率を与える）。
- `装備補正(+%)` / `状態変化補正(+%)`: それぞれ独立した層として乗算する。`(+%)`は割増を意味し、例えば+10%なら1.1倍。

**レイヤー内は加算、レイヤー間は乗算（決定事項）**: 上式の `装備補正(+%)` / `状態変化補正(+%)` は、それぞれが**単一の乗算項**である。同一レイヤー内に複数の補正が存在する場合（装備5スロット分、あるいは併存する複数の状態変化、5.4参照）、それらは**加算合成**して1つの項にまとめる。

```
装備補正(+%)     = 1 + Σ(各スロットの補正値)
状態変化補正(+%) = 1 + Σ(各状態変化インスタンスの effect_rate)
```

例えば `+10%` の状態変化が2つ併存する場合は `×1.2` であり、`×1.21` ではない。

**なぜ装備補正と状態変化補正を別レイヤーで乗算するのか**: 片方の陳腐化を防ぐため。両者を1つの補正値にまとめてしまうと、片方の強化が他方の存在意義を薄めやすい。この理由はレイヤー**間**にのみ当てはまり、同一レイヤー内の複数インスタンスには当てはまらない。したがってレイヤー内は加算とする。

**加算合成の帰結**: 乗算合成であれば補正値は決して負にならないが（`×0.5` を何回掛けても正）、加算合成では強力なデバフが重なることで DEF 等が負値を取りうる（`-60%` が2つで `1 - 1.2 = -0.2`）。5.1 が `max(0, ...)` のクランプを維持している理由はこれである。

**Speed・Luckは対象外（決定事項）**: SpeedとLuckは上記の`Scale × Shape`の枠組みに含まれず、それぞれ独自の計算式を持つ。

| ステータス | 基本値 | 変動要因 |
|---|---|---|
| Speed | 固定値。プレイヤーは基本500。敵は個別の基本値を持つ（`chido_enemy_master.speed`） | 装備効果のみ（正負どちらも取りうる）。強さ倍率・状態変化補正は影響しない（現時点） |
| Luck | 割合。基本0%（プレイヤー・敵共通） | 装備効果のみ（正負どちらも取りうる）。強さ倍率・状態変化補正は影響しない（現時点） |

**装備補正の表現形式（決定事項）**: HP・攻撃力・防御力系は`+%`（割増）。Speedは絶対値の加減算（例: +50、-30）。Luckは%ポイントの加算（例: +5% → Luck 5%）。

**将来拡張のための設計方針**: 状態変化によるSpeed/Luckへの影響は現時点では無しとするが、将来的に解禁する可能性があるため、状態変化の対象ステータス（現状の効果対象=HP/攻撃/防御）に決め打ちした設計にはしない（5.4参照）。

### 2.4 属性の所在（決定事項）

ダメージ計算で参照される**実効属性**は、以下の和集合として算出される。

```
実効属性 = 本体属性 ∪ 装備属性 ∪ 一時付与属性
```

| エンティティ | 本体属性 | 装備属性 |
|---|---|---|
| プレイヤー | **常に `0`（属性なし）**。対応するデータを持たない | 装着中の全スロットの `elements` の OR |
| 敵 | `chido_enemy_master.elements` | 装着中の全スロットの `elements` の OR |

- **プレイヤーの属性は装備由来のみ**。装備なしのプレイヤーは `elements = 0`（属性なし）となり、ダメージ計算では属性相性計算自体が省略される。**この省略は仕様上の分岐ではなく実装上の最適化である**。5.3 の補正式は総当たりの対象集合が空なら自明に `x = 0` を返し、`1.3^0 = 1.0` となるため、計算を省いても結果が変わらない、というだけの話である。
- 敵側も同様に装備属性を OR する。プレイヤーと敵を対等に扱う原則に従う。
- 装備が属性を持つかどうかは手動設定に委ねる。実運用上、大半の装備は `0`（属性なし）を設定し、胴・アクセサリなど特定部位にのみ属性を与えるといったバランス調整を想定する。
- 一時付与属性の上限は設けない（5.3・5.4参照）。

**`0`（属性なし）と `Neutral`（無属性）の関係（決定事項）**: `elements = 0` は相性計算をスキップするため、結果的に「すべての属性に等倍」となる。これは `Neutral` 単体を持つ場合と同等の結果でなければならず、したがって**10×10相性表において `Neutral` の行・列はすべて ×1.0 である**ことが制約として確定する（5.3参照）。

両者はダメージ計算上は同一の挙動になるが、表示において区別しうるため、`Neutral` ビットは残す（かつては「モーション属性に反応する効果」での区別も理由に挙げていたが、11.2-8 の決定によりモーション属性への反応は不要となった。11.4参照）。

### 2.5 装備システム

装備は「ステータス補正の1レイヤー」であると同時に、「属性の供給源」「装備限定スキルの供給源」でもある（装備限定スキルは概念としては確定だが、実装は将来対応とする。11.4参照）。

- 補正の表現形式は2.3の通り（HP/ATK/DEFは`+%`、Speedは絶対値加減算、Luckは%ポイント加算）。
- スロットは weapon / head / chest / legs / accessory1 の5枠。敵側も完全に対称なスロット構造を持つ。
- 装備限定スキルは習得済みスキルのテーブルに保持せず、装備側から動的に参照する。参照経路の具体的な設計は将来検討とする（11.4参照）。
- 敵の装備は出現（spawn）時に抽選で確定し、セッション中に変化しない。撃破時に一定確率でドロップする。

**戦闘中の装備変更を許容する（決定事項）**: ステータスはレベルと装備から毎回動的に算出されるため、装備変更は即座に戦闘へ反映される。

- 装備変更により最大HPが減少した場合、現在HPのクランプは行わない（3.4参照）。
- 装備変更により実効属性が変わるため、同一セッション中に属性が変化しうる。
- **敵の装備は出現時固定であるため、この点においてプレイヤーと敵は非対称である**（意図的な非対称）。
- 装備変更と戦闘行動の競合は、7章のロックにより排他される。

## 3. 戦闘セッション・参加者・ターゲット

### 3.1 `BattleSession` / `BattleParticipant`

- `BattleSession` はDiscordの Guild/Channel/Message に紐づき、戦闘進捗は1つの埋め込みメッセージを編集して表示する。
- `BattleParticipant` は `IEntity` と `EntityType`（Player/Enemy）、プレイヤーなら `DiscordUserId`、敵なら `EnemyId`（`Guid?`。敵の出現インスタンスの識別子）を持つ。

敵の出現インスタンスから種族データを読み出し、単一の継承クラス `Enemy : EntityBase` に変換して運用する。データ駆動＋継承のハイブリッドとする。なぜなら、種族ごとにC#クラスを増やせばクラス数が際限なく膨らむためである。

#### 埋め込みにおける状態変化の表示（決定事項）

**表示スコープ**: 1回の戦闘行動に対するレスポンスでは、**そのターンで状態が変化したエンティティのみ**を表示する。1.2 の「1回のターンは1対1で完結する」という中核設計により、この集合は構造的に**最大3体**に収まる。

| 行動 | 表示されるエンティティ |
|---|---|
| `Attack` / `Skill` / `Defend` | 行動者 + `CurrentTarget`（対象かつ反撃者） → 2体 |
| `Use`（味方対象） | 行動者 + 対象の味方 + `CurrentTarget`（反撃者） → 3体 |
| 敵が味方対象スキルを使用 | 行動者（プレイヤー） + `CurrentTarget`（反撃した敵） + 敵が `ally_target_rule` で選んだ味方の敵 → 最大3体 |

`Use` は例外ではなく、この規則の自然な帰結である。敵の組が複数体でも、反撃するのは `CurrentTarget` の1体のみ（4.2参照）のため増えない。敵が `target_rule = 味方` のスキルで組の別の敵に作用した場合（11.2-5参照）も、影響を受けるのはその1体のみのため、同様に最大3体で収まる。

**表示形式**:

```
[<状態変化名>] (<残りターン>)
```

- 同一 `effect_key` の複数インスタンスは**1行に集約**し、残り有効行動数をカンマ区切りで併記する（例: `[毒] (3, 5, 8)`）。括弧内の要素数がそのまま重ね掛け数を表し、2.3 のレイヤー内加算の内訳が読み取れる
- 無期限（残り有効行動数が NULL、5.4参照）は `(∞)` と表記する
- 表示対象は `chido_battle_effect`（戦闘スコープ）と `chido_player_effect`（永続スコープ）の**和集合**。どちらも 2.3 の `状態変化補正(+%)` に加算されるため、片方だけでは表示と実ステータスが一致しない
- `ParticipantStatus.Active` の参加者に限る
- 状態変化の表示名は描画時に**16文字**で切り詰め、超過分は `…` とする（`chido_effect_master.name` は VARCHAR(100) のまま維持し、切り詰めは描画層の責務とする）

**表示しないもの**: 付与者、付与元スキル、`affect_reason`、効果量。これらは閲覧者依存の情報、または1戦闘行動のレスポンスとしては情報過多であるため、将来の「戦闘状況表示」コマンド（11.4参照）が担う。

**表示順（決定事項）**:

```
1. 無期限（∞）を先頭
2. 最短の残り有効行動数の昇順
3. effect_key（最終タイブレーク）
```

集約後は「種類」単位の並びとなる。無期限を先頭に置くのは「絶対に消えない＝常に効き続ける」という情報の重要度による。件数上限による略記（後述）で切り落とされるのが「最も遠くに消えるもの」になり、略記の切り口が情報の緊急度と一致する。`effect_key` は最終タイブレークとして順序の決定性を担保する（M1 で `joined_at` を順序キーから外したのと同じ方針）。

**表示上限（決定事項）**:

| 表示 | 参加者上限 | 状態変化上限 |
|---|---|---|
| 戦闘行動のレスポンス | 3（上記の規則により構造的に保証） | 15種類（超過分は「他 n 件」） |
| 戦闘状況表示（11.4参照） | 20人（超過分は「他 n 人」） | 5種類（超過分は「他 n 件」） |

**ただし実効的な制約は件数ではなく文字数である。** Discord の埋め込みには「フィールド数25 / フィールド値1024文字 / **メッセージ内の全埋め込み合計6000文字**」という制限があり、複数の埋め込みに分割しても合計6000は回避できない。`chido_effect_master.name` は VARCHAR(100)、残り有効行動数は最大5桁（5.4参照）であるため、1行は最悪111文字に達する。件数上限を満たしていても文字数予算を超えうるため、**描画層で予算超過時の一律縮退（またはページング）を最後の砦として実装する**。戦闘状況表示の「5種類」は、この6000文字予算から逆算した値である。

**縮退通知は縮退の対象外とする（B-10・決定事項）**: マスタデータ不整合により敵の抽選が草原フォールバックに落ちた場合（10.3参照）、およびフィールド遷移が草原フォールバックに落ちた場合（10.4参照）は、その旨を伝える固定の短い一文（例:「※このフィールドの敵データが不足しているため、草原の敵が出現しました。」）を表示する。この一文は**上記の文字数縮退の対象外**とし、予算計算には固定長として最初から算入する。縮退で真っ先に切り落とされると通知の目的そのものが失われるためである。配置（進捗埋め込みか行動レスポンスか）は別途決定するが、「縮退の対象外である」という要件は配置に依存しない。抽選側・遷移側の両フォールバックに同一の通知規則を適用する（片方だけ黙る状態を作らない）。

### 3.2 参加者の状態（決定事項）

参加者の生死・離脱状態は、**状態そのものを一次情報として保持する**。`CurrentLife == 0` からの間接的な判定には頼らない。

```csharp
public enum ParticipantStatus
{
    Active,
    Escaped,
    Defeated,
}
```

**なぜ**: 「HP=0=戦闘不能」という固定的な対応関係だけでは、今後の拡張（例: 戦闘不能でも一定条件で復帰する、HPが0でなくても戦闘から除外される等）に対応しづらくなる。状態を独立した情報として持つことで表現の幅を残す、という判断。

3.4 の通り、現在HPは `MaxLife` を超えうる。「戦闘不能」の判定根拠を `CurrentLife` に置けない以上、状態列は必須である。

**`ParticipantStatus` は `EntityType` を問わず全参加者に適用される（決定事項）**。敵もスキルの戦闘離脱モーション（4.2参照）により `Escaped` になりうる。

この状態は物理削除されず、戦闘終了後も参照可能な形で保持され続ける（8.1参照）。

### 3.3 ターゲット（`CurrentTarget`）概念

Attack/Skill/Defend が「対象1体との1ターン」として成立するために、参加者ごとに「現在相対している敵」を保持する概念を導入する。

- `/target [対象]` で明示的に設定。
- `/attack [対象]` のように行動コマンド側で都度指定することも可能（`[対象]` はオートコンプリート付きの任意入力文字列、9.2参照）。
- 一度指定した対象は、明示的に変更するまで保持され続ける（＝「今はその敵と相対している」という状態として再定義）。

**ターゲットの解決（単一の導出関数・決定事項）**

`CurrentTarget` の解決は、初回既定・自動失効後の再選定を区別せず、**単一の導出関数**で行う。

```
ResolveTarget(actor):
    stored = actor.current_target_id
    if stored ≠ NULL かつ stored の参加者が ParticipantStatus.Active:
        return stored
    return Participants 中で entity_type = Enemy かつ Active な、display_order 最小の参加者
```

- 参加時の `current_target_id` は `NULL` のまま（初期化のための書き込みを行わない）。プレイヤーが一度も対象を指定していない初回も、対象が戦闘不能等でいなくなった場合も、この関数の後段（`Active` な先頭の敵）に落ちる。「初回だから」「対象が死んだから」という契機による分岐は持たない。
- 後段に落ちた場合、その結果を `current_target_id` に**書き戻す**（決定事項・方式b）。3.3 の「自動解除され次点が選定される」という語のとおり、格納値をその時点で確定させる。書き戻しは行動処理と同一トランザクション内で行い、チャンネル行ロック（7.2参照）に包摂されるため追加のロックは不要。書き戻す設計により、明示指定した敵Aが戦闘不能になった後（将来の蘇生機能で）復活しても、ターゲットは巻き戻らない。
- `Active` な敵が1体も存在しない状態でこの関数が呼ばれることは、4.3 のセッション終了トリガー（敵側の生存が0で `PlayerVictory`／`EnemyEscaped`）により構造的に起こらない。到達したらフォールバックせず実装の不具合として例外を投げる（無言で行動を握り潰すと、セッション終了処理の漏れが検出できなくなる）。

後段の「`ParticipantStatus.Active` を保つ、先頭の敵」の「先頭」の順序は、敵の組（10.3参照）における `member_index` の昇順に対応する。この順序はDiscord埋め込み上の表示順とも一致する。

**敵の指定は反撃者確定より前に書き込む（決定事項）**: `[対象]` に敵が指定された場合、`current_target_id` の更新は、そのターンの反撃者が確定する（＝A-8 の関与者集合が閉じる、5.4参照）**前**に行う。これにより「このスキルで自分を強化しつつ、どの敵から反撃を受けるかを決める」という用法が成立する。更新を反撃者確定より後に置くと、更新した対象は次ターンからしか反撃者にならず、指定の意図が失われる。

**なぜこの基準なのか**: (1) 選定結果が常に一意になり、(2) プレイヤーから見ても「一番上に表示されている敵」＝「次にターゲットされる敵」という直感と一致する、という二重のメリットがある。HPが低い順など動的に変わる基準は、行動の度に順位が入れ替わり予測しづらくなるため避けている。

**順序の根拠（決定事項）**: この順序の唯一の根拠は `chido_battle_participant.display_order` である。**参加時刻（`joined_at`）は順序付けに使用しない**。

| `entity_type` | `display_order` の値 |
|---|---|
| Enemy | `chido_channel_current_enemy.spawn_index`（＝組の `member_index`）をそのまま複製する。ターゲット自動再選定における「先頭の敵」の唯一の根拠 |
| Player | セッション内の参加順。参加時に同一 `(session_id, entity_type=0)` の最大値+1 を採番する（初参加は `0`）。Discord埋め込みの表示順にのみ使用され、ターゲット選定には使用されない |

**なぜ `joined_at` を使わないのか**: 敵の組は全メンバーが同一トランザクションで一括投入されるため、`joined_at` がミリ秒精度で同値になり順序が一意に定まらない。これが発端だが、プレイヤー側も安全ではない。参加処理はチャンネル行ロック（7.2参照）で直列化されるが、直列化は「同時に走らない」ことを保証するだけであり、`DATETIME(3)` が別ミリ秒になることは保証しない。**時刻を順序キーに流用していたこと自体が原因**であるため、敵・プレイヤーの双方で外す。

**なぜ `entity_type` ごとに独立した番号空間なのか**: 敵側は `member_index` → `spawn_index` → `display_order` が恒等の複製となり、値の再導出やオフセット加算が入らない。マスタの `member_index = 2` の敵は参加者行でも `2` であり、追跡が単純になる。単一空間にしてプレイヤーにオフセットを振ると、この対応が壊れ、かつ「プレイヤーは敵の後ろ」といった表示方針をスキーマに埋め込むことになる。埋め込みの並べ方はプレゼンテーション層の判断として C# 側に残す。

**欠番の扱い**: `Escaped` / `Defeated` の行は物理削除されないため（3.2・8.1参照）、離脱者の番号は空かない。離脱後の再参加で新しい `entity_id` の行が生まれた場合は `MAX+1` により末尾に付く。順序としては「参加順」の意味が保たれるため、欠番の詰め直しは行わない。

複数プレイヤーが同一の敵を同時にターゲットすることは許容される（1体の敵に対して複数プレイヤーが同時に相対する状況は通常の戦闘として想定内）。

### 3.4 現在HPと戦闘ごとの全快（決定事項）

**現在HPの真値は、参加者（`BattleParticipant`）が持つ値のみ**である。プレイヤー単位の永続的な現在HPは保持しない。

- セッションへの参加時、現在HPはその時点のレベル・装備から算出した `MaxLife`（＝全快）で初期化される。
- したがって**戦闘ごとに全快する**。これは意図した仕様であり、その帰結として戦闘外の回復手段は設計上存在しない。
- TPも参加時に0で初期化される。

**現在HPのクランプは一切行わない（決定事項）**。`現在HP > 最大HP` の状態（オーバーヒール）を許容する。これは回復効果を受けた場合、装備変更により最大HPが減少した場合など、戦闘中における全ての現在HP変動に共通する。オーバーヒール状態は、次のセッション参加時に `MaxLife` が書き込まれることで自然に解消される。

**なぜクランプしないのか**: `MaxLife` は装備・状態変化から毎回動的に算出される値であり、「現在HPを最大HPに合わせて切り詰める」処理は、装備変更や状態変化の付与・解除のたびに走ることになる。切り詰めた値は元に戻らないため、「装備を一時的に外して戻すとHPが減る」といった不可逆な副作用を生む。クランプしないことで、`MaxLife` の変動を現在HPから完全に独立させられる。

## 4. ターン順・行動処理モデル

### 4.1 行動順（Priority → Speed → Random・決定事項）

1回のターンに関与する2エンティティ（行動したプレイヤーと対象の敵）の行動順は、以下の3段のキーで決定する。共有ターンキュー（1.2参照）が存在しないため、この順序はあくまで「そのターン内の先攻・後攻」に限定される。

```
OrderBy(Priority) → ThenBy(Speed) → ThenBy(Random)   （いずれも降順・先攻が先）
```

1. **`Priority`（行動優先度）**: 使用スキルが持つ整数値（`chido_skill_master.priority`）。大きいほど先攻。既定は0（Attack・通常スキル）で、Defendには正の値を与える。
2. **`Speed`（素早さ）**: `Priority` が同値のとき、`Speed`（2.3参照）の降順で決定する。
3. **`Random`（乱数タイブレーク）**: `Priority` も `Speed` も同値のとき、そのターンで**1回だけ**引いた乱数で先攻・後攻を決める。

先攻側の一撃で後攻側が戦闘不能になった場合、後攻側の行動は**キャンセルされる**（＝ダメージ計算自体が行われない）。

**なぜ `Priority` を導入するのか（決定事項）**: `Priority` を持たず `Speed` のみで行動順を決めると、Defendの有効性が `Speed` だけで決まってしまう。Defendは「相手の攻撃を受ける前に軽減の構えを取る」行動であり、鈍足側がDefendしても先に被弾してから構えが立つため無意味になる。これはプレイヤー・敵の双方に対称に生じる欠陥である。Defendに高い `Priority` を与えることで、`Speed` に関わらず先んじて構えを取れるようにし、この欠陥を解消する。

**乱数タイブレークの一意性（決定事項）**: `Random` の抽選は**そのターンにつき1回だけ**引き、その結果を**行動の実行順とログの整形順の両方**に使う。行動順を決める抽選とログの並び順を別々に引くと、ログが実際の処理順とずれる。非同期・サーバ側解決（7.2のロック下）で解決される以上、この一致は明示的に縛る。なお、これは行動順のタイブレークであり、埋め込みの**表示ソート**（`display_order` 等による安定ソート、3.3参照）とは別レイヤーである。

**`Priority` はバランスレバーでもある（設計上の帰結）**: 高 `Priority` の攻撃スキル（「先制攻撃」）は、上記の「先攻の一撃で後攻が戦闘不能ならキャンセル」を能動的に狙う手段になる。5.1 の勝敗分水嶺（`E ≤ L`、1行動につき1反撃を前提）自体は崩れないが（同格は一撃で倒せない）、`Priority` は撃破順の奪い合いに新しい軸を持ち込む。10.4 のフィールド設計と並ぶ調整つまみとして位置づける。

### 4.2 行動タイプごとの挙動

| ActionType | 対象決定 | 相手の反撃 | ターン消費 | 備考 |
|---|---|---|---|---|
| `Attack` / `Skill` | モーションの `target_rule` に従う | あり | 1セット | 基本のターンモデルそのもの |
| `Defend` | モーションの `target_rule` に従う | あり（軽減後） | 1セット | 自分自身に「ダメージ軽減率（DRR）」の状態変化を付与し、そのターンの被ダメージを軽減する（5.1・5.4参照）。半減（DRR 50%）が既定。効果量は今後の拡張で変動しうる |
| `Use`（戦闘用アイテム） | モーションの `target_rule` に従う | あり | 1セット | 対象が自分/味方であっても、`CurrentTarget` からの反撃とセットで1ターンとして処理する |
| `Escape` | なし | **なし** | セッションから離脱 | 下記4.3参照 |

**Defend が成立する理由（決定事項）**: Defendは「防御」という1つのスキルとして表現され、その実体は **`target_rule = 自分自身` の状態変化付与モーション1つ**（`duration_actions = 1` の DRR 効果を自分に付与、反撃モーションなし）である。5.4 の減衰規則（両者の行動終了後・ターン終了の直前に -1）により、付与されたそのターンの相手の一撃までは軽減が有効で、ターン終了で消える。4.1 の `Priority`（Defendに正値）により、`Speed` に関わらず被弾前に構えを取れる。

- **軽減の対象は「`CurrentTarget` からの被ダメージ」ではなく、そのターンに自分が受ける全ダメージである**。DRRは被弾側に付与された状態変化であり、ダメージの出所（付与者）を問わない。1対1のターンモデルでは結果的に `CurrentTarget` からの被弾しか存在しないため「半減」と等価に見えるが、規則としては全被ダメージへの軽減である。ただし `SlipDamage`（継続ダメージ）にはDRRを適用しない（5.1参照）。
- 軽減の具体的なフェーズ・合成規則・下限は 5.1（PostDefenseでのDRR適用）を正とする。

#### モーション種別（決定事項）

スキルは1つ以上のモーションから構成され、`motion_index` 昇順に再生される。モーションの種別は以下の4種。

| `motion_type` | 種別 | 固有パラメータ |
|---|---|---|
| 0 | 攻撃 | `attack_type` / `power` / `elements` |
| 1 | 回復 | `attack_type` / `power` |
| 2 | 状態変化付与 | `effect_key` / `effect_rate` / `attack_type` / `duration_actions` |
| 3 | 戦闘離脱 | なし |
| 4 | 状態変化解除 | `effect_key` |

攻撃と回復は**列構成も意味論も異なる**。属性（`elements`）は攻撃モーションのみが持ち、回復・状態変化付与・解除・戦闘離脱は属性を持たない（5.3参照）。加えて 5.1 の被防御係数、5.2 のクリティカル、5.3 の属性相性は攻撃にのみ適用される。したがって攻撃と回復は別サブタイプであり、`motion_type` を廃して `power` を符号付きにするような統合は行わない。

全モーションが共通して持つのは `target_rule` / `accuracy_rate` / `accuracy_gate_group` の3つ。`accuracy_gate_group` は命中判定の依存グループを表し、既定は無指定（そのモーション単独で判定する）。詳細は下記「命中判定と道連れ（`accuracy_gate_group`・決定事項）」を参照。

#### 対象の解決規則（`target_rule`・決定事項）

`target_rule` は**モーション単位**で持つ。**これは「プレイヤーが選ぶ選択肢」ではなく「対象をどう解決するかの規則」であり、3つの値のうち2つはユーザー入力を一切消費しない。**

| `target_rule` | 解決規則 | ユーザー入力 |
|---|---|---|
| 自分自身 | 行動者そのもの。`[対象]` の指定があっても対象は変わらない | 不要 |
| 敵 | `CurrentTarget`（3.3参照） | 不要 |
| 味方 | コマンドの `[対象]`。省略時は行動者自身 | 任意 |

**「味方」は自分自身を含む（決定事項）**: `target_rule = 味方` の解決対象は自軍側の `ParticipantStatus.Active` な参加者であり、**行動者自身を含む**。`[対象]` が省略された場合は行動者自身に解決する。これにより、同一のスキルエントリが `/skill heal`（自己回復）と `/skill heal @味方`（味方回復）の双方として機能し、スキルデータの倍増を避けられる。

**`自分自身` と `味方` の差（決定事項）**: 省略時の結果（＝行動者）は両者で一致するが、`[対象]` を指定されたときの挙動が異なる。`味方` は指定された味方に解決するが、`自分自身` は指定を無視して常に行動者に解決する（「自分を強化」のように、味方に向けられては困る効果のための、より強い規則）。両者は別規則として併存する。

**`[対象]` は常に受理する（決定事項）**: `[対象]` の受理可否はスキル構成に依存しない。解決された参加者の `entity_type` によって役割が決まる。

| 解決先 | 役割 | 入力の反映 |
|---|---|---|
| 敵 | `CurrentTarget` を更新（3.3参照）。そのターンの反撃者を決める | 常に反映される |
| 味方（自分を含む） | `target_rule = 味方` のモーションの対象として供給 | 該当モーションが1つも無ければ空振り → 通知 |

敵の指定はスキル構成を問わず必ず意味を持つ（反撃者の決定という全スキル共通の経路を通るため）。空振りしうるのは味方の指定のみである。したがって、`自分自身` のみのスキルに敵を `[対象]` として指定する行為は「自分を強化しつつ、どの敵から反撃を受けるかを決める」正常な用法であり、拒否しない。

**空振りの通知（決定事項）**: 次の3条件をすべて満たす場合、レスポンスで「○○ への影響はありませんでした。」と通知する。

1. `[対象]` が味方に解決された
2. 解決先が行動者自身ではない
3. 実行スキルが `target_rule = 味方` のモーションを1つも持たない

「入力が結果に反映されなかったことを必ず通知する」という 5.4 の規則（重複付与時の拒否通知・解除モーションの空振り通知）と同型である。解決先が行動者自身の場合は、`自分自身` のモーションが実際に作用しているため通知しない（事実に反する通知を避ける）。この判定はスキルのモーション列の静的な構成によるものであり、実行時の失敗（命中失敗・対象状態によるスキップ・重複拒否）とは別レイヤーである。

**`[対象]` に非 `Active` を指定した場合（決定事項）**: `Escaped`／`Defeated` の扱いは非対称である（将来の蘇生スキルのための布石）。

| 対象の状態 | 指定 | 結果 | メッセージ |
|---|---|---|---|
| `Active` | 可 | 通常処理 | — |
| `Defeated` | 可（解決はする） | 常に拒否。行動が不成立となり、ターン・TP・反撃・状態変化の減衰のいずれも発生しない | 「○○は既にやられています。」 |
| `Escaped` | 不可（候補集合に存在しない） | 解決不能として拒否 | 「○○は戦闘から離脱しています。」 |

いずれも**行動の不成立**であり、5.4 の重複付与時の「拒否」（モーションは実行される）とは別物である。行動が成立していないため `current_target_id` は書き換えず、5.4 の減衰（A-8）も起きない。この拒否ゲートは対象解決の直後・ターン開始の直前に置き、`Defeated` の可否を「実行スキルが蘇生モーションを含むか」で切り替えられる形にする（現行はその条件が常に偽）。`Escaped` は候補集合そのものから除外されるため、この分岐の対象外である。

**なぜスキル単位ではなくモーション単位なのか**: 5.3 が例に挙げる「自分を強化（無属性）」→「火属性の攻撃」という2モーション構成のスキルは、1モーション目の対象が自分、2モーション目の対象が敵である。スキル単位で対象を1つしか持てないと、このスキルは表現できない。ドレイン（敵を攻撃して自分を回復）も同様。

**UIへの波及はない**: 上記の例は「自分自身 + 敵」の組み合わせであり、どちらも入力を消費しない。`[対象]` は**コマンドの引数であってモーションの引数ではない**ため、1スキル内に味方対象モーションが複数あっても、すべてが同じ1つの `[対象]` に解決される。曖昧さが生じる余地はない。

**`CurrentTarget` との関係**: `target_rule` は「どの解決規則を使うか」を指定し、そのうち「敵」の規則が `chido_battle_participant.current_target_id` を読む。両者は別概念ではなく、上位・下位の関係である。`current_target_id` の解決は初回既定・自動失効後の再選定を区別せず、単一の導出関数で行う（3.3参照）。

**命名について**: かつて `chido_skill_master.range_type`（影響範囲種別）と呼ばれていたもの。`range`（範囲）は AoE や射程を連想させるが、影響範囲は常に単体固定であり範囲という概念は存在しない。実体は対象の解決規則であるため `target_rule` に改称した。

**Use（戦闘用アイテム）の位置づけ**: 「戦闘ステータスに作用するアイテム」はすべて「戦闘用アイテム」として分類され（`chido_item_master.item_type = 0 (battle)`）、対象が自分であっても敵からの反撃とセットの通常行動として処理される。回復アイテムを使ったターンも無防備になる、という設計。アイテムの効果は「特定スキルの発動」（`use_skill`）に収束するため、スキル発動ロジックをそのまま再利用できる。

**通常攻撃（Attack）とスキル（Skill）の関係（決定事項）**: Attackは「対象に威力100%の無属性物理攻撃」という単一モーションを持つ、スキルマスタ上の通常のスキルエントリとして表現される。特別扱いされる別実装ではない。マスタデータはエンティティ種別（プレイヤー/敵）を問わず共通のため、Attackのスキルエントリもプレイヤー・敵間で単一の行として共有される。

**Defendの位置づけ（決定事項）**: Defendも同様に「防御」という1つのスキルとして表現されるが、その効果は被ダメージ軽減**のみ**であり、反撃モーションは含まない。実体は上述の通り「自分自身へのDRR付与モーション1つ」である。Attackと同じく、全プレイヤーが習得手続きなしに最初から使用できる（11.3参照）。DefendのスキルはAttackと同様、敵の抽選プールにも登録されうる（敵も防御を選択しうる。4.1 の `Priority` により敵のDefendも被弾前に構えを取れるため、プレイヤーと敵は対称に機能する）。

**敵の反撃モデル（決定事項）**: プレイヤーと敵は、互いに「1スキルに対し1スキル」で応酬する。1スキルが複数モーションを持つ場合、そのモーション集合は「1スキルの効果」として上から順に再生される。処理順は「行動側スキルの全モーション再生 → 相手側スキルの全モーション再生」という直列であり、並行処理は行わない。

**敵のスキル選択（決定事項）**: 敵は`action_pattern_type`（完全ランダム/重み付きランダム/ローテーション）に従い、保有スキルの中から反撃に使うスキルを選択する。通常攻撃も他のスキルと同様、抽選プールの1エントリとして登録されうる。

`weight`（抽選の相対重み）は **`重み付きランダム` でのみ参照される**。`weight = 0` はそのパターンにおいて「抽選対象外」を意味するが、完全ランダム／ローテーションでは `weight` 列自体が無視されるため、`weight = 0` のスキルも通常通り使用される（意図的な非対称）。

**敵の味方対象モーションの解決（`ally_target_rule`・11.2-5・決定事項）**: 敵が `target_rule = 味方` のモーションを実行する場合、敵にはプレイヤーのような `[対象]` 入力も `CurrentTarget` の流用もないため、対象を別の規則で解決する。この規則は `chido_enemy_master.ally_target_rule` が敵の種族単位で保持する（スキルの選択規則である `action_pattern_type` と対をなす、対象の選択規則）。

候補集合は自軍側の `ParticipantStatus.Active` な参加者（実行者自身を含む）であり、「味方」に自分を含む点はプレイヤー側（11.2-6）と対称である。現行では以下の3規則のみを実装する（他は将来拡張として `ally_target_rule` の予約値に割り当てる。DB 11番参照）。

| 値 | 規則 | 内容 |
|---|---|---|
| 0 | 完全ランダム | 候補（自分を含む）から完全ランダムに1体 |
| 1 | 自分以外からランダム | 候補から自分を除いた集合からランダム。空なら自分 |
| 24 | 最小HP割合 | 候補のうち `CurrentLife ÷ MaxLife` が最小の集合からランダム |

- **単独なら自分**: 「味方」が自分を含むため、値0・24では候補が空にならず、単独時は自然に自分が選ばれる。明示的なフォールバックが要るのは候補を意図的に狭める値1（および将来の固定対象系）のみ。
- **HP割合は除算せず交差乗算で比較する（値24）**: `MaxLife > 0` が常に保証される（2.3・10.5）ため、`a.CurrentLife × b.MaxLife < b.CurrentLife × a.MaxLife` で比較し、浮動小数点を通さない（6.2・2.3と同じ方針）。オーバーヒール（割合が1超、3.4）もこの比較で自然に扱える。
- **「HP0を除外」はフェイルセーフ**: 候補集合は `Active` で定義し（正常系）、値24 の内部で追加条件 `CurrentLife > 0` を持つ（異常系。3.2 の「HPが0でなくても除外されうる」の逆＝「HP0だが `Active`」が生じた場合に、割合0の瀕死者へ回復対象が固定される退化を防ぐ）。2.3 のレベルクランプと同じ、正常系を状態で・異常系を値で塞ぐ二重防御である。
- **同値タイブレークのランダムは 4.1 の乱数とは別系統**: 4.1 の「そのターンにつき1回引く乱数」は行動順・ログ整形順を支配するものであり、対象選択の同値タイブレークは同一の乱数源から独立に引く（再現性のため）。
- **規則は敵単位である帰結**: 1体の敵が持つ複数の味方対象スキルはすべて同じ規則で対象を選ぶ。「取り巻きを回復しつつ自分だけを強化」は、強化側モーションを `target_rule = 自分自身` にすることで表現する（`target_rule` がモーション単位であることが逃げ道を用意している）。

**敵のTPと `require_tp` 判定（決定事項）**: 敵も `chido_battle_participant.current_tp` を持ち、スキル発動時に `require_tp` を消費する（プレイヤーと対称、4.4参照）。敵の初期TPは**敵マスタが持つ初期値**（`chido_enemy_master.initial_tp`）で初期化される。プレイヤーは常に初期TP0で初期化されるため、この点は非対称だが、実害はないため現時点では拡張として据え置く（プレイヤー側にも初期TPを持たせる拡張余地を残す）。

`require_tp` を払えないスキルの扱いは `action_pattern_type` により分岐する（**決定事項**）。

| `action_pattern_type` | `require_tp` 不足時の挙動 |
|---|---|
| 0（完全ランダム） | `require_tp` を満たすスキルのみで抽選プールを構成し、その中から等確率で抽選する。プールが空なら通常攻撃へフォールバック |
| 1（重み付きランダム） | `require_tp` を満たすスキルのみで抽選プールを構成し、**残存エントリの `weight` をそのまま用い、その合計で正規化して**抽選する。プールが空なら通常攻撃へフォールバック |
| 2（ローテーション） | ローテ順で選択されたスキルが `require_tp` を満たさない場合、そのターンは通常攻撃へフォールバックする（順番は飛ばさない。下記ローテーションの状態保持を参照） |

**なぜ挙動を分けるのか**: ランダム系（0/1）で「払えないスキルも抽選対象に含め、当たってから通常攻撃に落とす」方式にすると、存在するはずのないエントリが抽選される不自然さが生じる。よって払えるものだけでプールを構成する。ローテーション（2）は順序そのものに意味があるため、払えないときに「飛ばして次へ」進めると順序が崩れる。よって選択自体はローテ順を維持し、出力だけ通常攻撃に差し替える。

**ローテーションの状態保持（決定事項）**: ローテーションの現在位置は `chido_battle_participant.rotation_index` で保持する。敵の出現時に0で初期化され、敵が行動するたびに（選択スキルの成否・`require_tp` フォールバックの有無に関わらず）`(rotation_index + 1) % total` で進める。`total` は `chido_enemy_skills_master` の登録行数であり、**戦闘中は不変**である（いかなる要因でも敵の登録スキル数は変動しない）。1対1では結果的に `rotation_index = (turn - 1) % total` に一致するが、これは観測される従属式（テスト期待値・説明用）であって決定規則ではない。真実の情報源は `rotation_index` 列である。

**なぜ `rotation_index` を列で持つのか**: `(turn - 1) % total` を決定規則にすると、複数の敵が同一ターンに行動する構成（多対多への拡張）で全敵のローテ位置が同じ `turn` を参照して同期してしまう。例えば「ローテ末尾で自己バフをリフレッシュし先頭に戻る／プレイヤーがそれを妨害して不発にさせる」というデザインは、位置が同期・ずれると成立しない。敵インスタンス単位の `rotation_index` 列で持てば、多対多でも各敵が独立してローテを進められる。

**通常攻撃へのフォールバック（決定事項）**: 以下のいずれかの場合、例外処理として通常攻撃を行う。

- 敵が1つもスキルを保有しない
- `重み付きランダム` かつ、保有スキルの `weight` がすべて `0` で抽選プールが空になる
- 上記の `require_tp` 不足によるフォールバック（`action_pattern_type` 別、上表）

**「登録された通常攻撃」と「フォールバックの通常攻撃」の区別（決定事項）**: 両者は別物である。

- **登録された通常攻撃**: `chido_enemy_skills_master` にAttackの `skill_key` が1行として登録されているもの。ローテ枠を1つ占め（`total` に数えられる）、ランダム系では抽選候補になり、ローテでは順番が回れば選ばれる。`require_tp = 0`（Attackは前提としてTP不要）のため必ず払え、フォールバックを誘発しない。
- **フォールバックの通常攻撃**: 登録スキルが払えなかった結果として差し込まれる出力。ローテ枠を持たず（`total` に数えない）、`rotation_index` は本来選ばれるはずだったスキルの位置として進み、その回の出力だけがAttackに差し替わる。

**両者のTP蓄積は同一経路に合流する（決定事項）**: いずれのAttackでも、実際にAttackモーションが再生された時点でTP+100が発火する（4.4参照）。TP契機を「Attackモーションの再生」に紐づけることで、「どちらのAttackか」を判定する分岐そのものを消し、フォールバックのAttackでもTPが蓄積される（＝敵がTP不足から抜け出せなくなる硬直を回避する）。

**モーション再生の5ステップ（決定事項）**: 各モーションは `motion_index` 昇順に、以下の順で再生される。ステップ2〜4は独立に働き、いずれか1つでも該当すればそのモーションはスキップされる。

```
1. 行動者が Active でなければ → 以降の全モーションを打ち切り（下記ショートサーキット）
2. accuracy_gate_group ゲート判定 → 同一グループの先頭が効果適用に到達していなければ、そのモーションのみスキップ
3. target_rule で対象を解決し、対象がそのモーションの要求する状態でなければ → そのモーションのみスキップ
4. 命中判定（accuracy_rate）→ 外れたら、そのモーションのみスキップ
5. 効果適用
```

「モーションの要求する状態」は現行では全モーションが `Active`。将来の蘇生モーションのみ `Defeated` を要求する（前述の受理層ゲートと同一の概念であり、実装も1箇所に集約する）。

**先攻が後攻を撃破した後の残モーション（A-2・決定事項）**: 複数モーションの途中で対象（`target_rule` により解決される適用対象）が戦闘不能・離脱した場合、以降のモーションはステップ3の対象状態判定に従う。対象が `Active` なら再生し、`Defeated`／`Escaped` なら**そのモーションのみ**スキップする。行動者自身は `Active` のままであるため、末尾に自分自身対象のモーション（自己バフ等）があれば相手撃破後も再生される。これは対象の生存判定であって、行動者の生存判定（ステップ1）とは独立である。

**命中判定と道連れ（`accuracy_gate_group`・決定事項）**: 「攻撃が命中したら n% で毒を付与する」のように、モーションの成否を他モーションの前提条件にするための仕組み。同一 `skill_key` 内で同じ `accuracy_gate_group` を持つ行が1グループを成し、`motion_index` 最小の行を先頭とする。

- 先頭が**効果適用に到達した**場合、同一グループの他メンバーはそれぞれ自身の `accuracy_rate` を独立に抽選する（先頭が命中しても、他メンバーが自動成功するわけではない）。これにより「攻撃命中 → 毒30% ＆ 麻痺20% をそれぞれ独立判定」が表現できる。
- 先頭が到達しなかった場合、同一グループの他メンバーは抽選を行わずスキップされる。
- 依存先は常に**先頭1件**であり、直前のメンバーではない。メンバー同士は連鎖しないため、1攻撃から複数の状態変化を付与できる（ショートサーキット方式ではこれが困難になるため採らない）。
- `accuracy_gate_group` が無指定のモーションは、他に依存せず単独で判定する（現行挙動）。

「効果適用に到達」の判定は命中成功と同一ではない。先頭が対象状態でスキップ（ステップ3）または命中失敗（ステップ4）した場合は到達せず、グループ全体がスキップされる（倒した相手・外した攻撃に毒を乗せない）。一方、状態変化の重複付与による拒否や解除モーションの空振り（5.4）は「モーションは実行された」側に分類されるため到達扱いとなる。ゲートによりスキップされたメンバーには個別通知を出さない（先頭の失敗が既に通知されており、帰結が自明であるため）。

**スキルモーション列内の「戦闘離脱」（決定事項）**: スキルのモーション列に「戦闘離脱」が含まれる場合、`motion_index`昇順の再生順において、それより前のモーションはすべて通常通り再生された上で、**離脱に成功した場合に限り**、その再生時点をもって以降のモーションはショートサーキットされ再生されない（上記ステップ1に相当。例: 「バフ付与→戦闘離脱」ならバフは発動した上で離脱、「戦闘離脱→追加攻撃」なら追加攻撃は発動しない）。戦闘離脱モーション自体は、`/escape`コマンドと同一の戦闘離脱処理をモーション経由で呼び出す（4.3参照）。

**戦闘離脱モーションは失敗しうる（決定事項）**: 戦闘離脱モーションも他のモーションと同様に `accuracy_rate`（成功率）を持つ。`/escape` コマンドがモーションを経由せず戦闘離脱処理を直接呼び出す（＝必ず成功する）のとは異なる経路である（4.3参照）。

- **ショートサーキットの条件**: ショートサーキットの根拠は「**行動者が**離脱したのなら、行動者の以降のモーションはもう再生されえない」という帰結であり、モーションの種別そのものではない。したがって全モーション共通のステップ1（行動者が `Active` か）に一般化される。離脱しなかったのなら以降のモーションを止める理由はないため、**行動者自身の離脱成功時のみ**打ち切る（「逃げようとして失敗したので殴る」が成立する）。なお `target_rule = 敵` の離脱モーションで敵を追い払った場合、打ち切られるのは敵対象モーションのステップ3（対象が `Escaped`）だけであり、行動者は `Active` のままなので末尾の自分自身対象モーションは再生される（A-2 と同じ規則）。
- **反撃の有無**: 追加の規則は不要であり、既存の処理順（行動側スキルの全モーション再生 → 相手側スキルの全モーション再生）から自動的に導かれる。離脱**成功**時は、反撃が再生される時点で行動者が既に `Escaped` であり反撃の対象が存在しない（結果的に `/escape` と同じ）。離脱**失敗**時は行動者が `Active` のまま残るため反撃が発生する。
- **リスク・リターン**: `/escape`（確実・反撃なし）に対し、離脱スキルは「他のモーションと組み合わせられるが、失敗すれば反撃を食らう」という位置づけになる。`accuracy_rate` がこの2経路を意味のあるものとして分離している。

**離脱モーションの対象（決定事項）**: 離脱するのは `target_rule` により解決された対象である。`target_rule = 敵` の離脱モーションはプレイヤーが敵を「追い払う」手段として成立し、4.3 の `EnemyEscaped` トリガーを発火させる。これは意図した表現である。3.2 が既に「敵もスキルの戦闘離脱モーションにより `Escaped` になりうる」と規定し、4.3 が `EnemyEscaped` を独立したトリガーとして設け、10.3 に抽選分岐まで用意しているため、敵が逃げる経路は既に設計に織り込まれている。

**その帰結**: `EnemyEscaped` では撃破報酬も累積敵レベルの上昇も発生しない（4.3・6.2・10.1参照）ため、「勝てない敵を追い払って引き直す」という手段が、既存仕様の合成だけで成立する。`accuracy_rate` がその成功率を調整する唯一のつまみとなる。

### 4.3 Escape とセッション終了トリガー

**Escapeの実行経路（決定事項）**:

- `/escape`コマンド：戦闘離脱処理を**直接**呼び出す。`Active`/`Defeated`いずれの状態からも実行可能（生死を問わない）。モーションを経由しないため `accuracy_rate` の判定が入らず、**必ず成功する**。
- スキルモーション種別「戦闘離脱」：同一の戦闘離脱処理を、モーション経由で**間接的に**呼び出す手段（4.2参照）。プレイヤー・敵のどちらもこの経路で離脱しうる。`accuracy_rate` を持つため**失敗しうる**。離脱するのは `target_rule` により解決された対象であり、プレイヤーが敵を離脱させることも表現できる。

どちらの経路で離脱した場合も、報酬を得られず（6.2参照）、離脱後は同じ戦闘に再参加できない。

**セッション終了トリガー（決定事項）**: 以下の3系統を並列に判定する。「戦闘不能」であること自体は終了トリガーに**含めない**。

| トリガー | 判定 | `end_reason` |
|---|---|---|
| 敵側の生存が0（撃破） | すべての敵が `Defeated` | `PlayerVictory` |
| 敵側の生存が0（逃走を含む） | すべての敵が `Escaped` または `Defeated` で、最後の1体の消失原因が `Escaped` | `EnemyEscaped` |
| プレイヤー側の生存が0 | すべてのプレイヤーが `Escaped` | `PlayerEscaped` |

**なぜ3系統に分けるのか**: 終了理由は次に出現する敵の抽選ロジックを分岐させる（10.3参照）。ところが参加者の状態分布からは、どのトリガーで終了したかを事後的に区別できない。例えば「敵2体のうち1体が逃走し、もう1体が撃破された」場合と「敵1体が逃走し、その後プレイヤーが全員逃走した」場合とで、テーブル上には `Escaped` の敵行と `Escaped` のプレイヤー行が同居しうる。したがって**トリガーが発火した時点で終了理由を明示的に記録する**。

**全参加者が戦闘不能でもセッションは終了しない**: 以下のいずれかが起きるまで残り続ける。

- 新規参加者が仕留めに来る（`PlayerVictory`）
- 戦闘不能の参加者を含め、全員が改めてEscapeを選択する（`PlayerEscaped`）

**「0人になる」の意味**: 3.2の通り、参加者の状態は一次情報として保持され、`Participants`リストから行が物理的に削除されることはない（8.1参照）。したがってここでの「0人」は、リストの行数が0になることではなく、**該当する側の全参加者の状態が `Escaped`（あるいは `Defeated`）に揃った**ことを指す。

**終了後の「リセット」**: 同一セッションを延命させるのではなく、次の敵の出現を伴って **新規に `BattleSession` を生成し直す**。次の敵の抽選は終了理由により分岐する（10.3参照）。

**なぜこの仕様なのか**: Escapeは**チャンネル消失などシステム都合で戦闘を継続できなくなる事態に対する詰み防止**という位置づけである。ゲームバランス上勝てない敵から降りるための救済ではない。ゲーム性の一部というより、非同期・長期間開きっぱなしになりうるセッションを確実に閉じるための安全弁。この位置づけのため、「戦闘不能」というプレイヤーの意思によらない結果は終了トリガーに含めず、あくまで各参加者の**能動的な選択**であるEscapeのみをトリガーとする。

非同期・飛び入り参加前提のため、参加者の総数はそもそも確定しない。したがって「戦闘不能」を終了トリガーに含めてしまうと、最初の1人が参加してそのまま戦闘不能になっただけでセッションが終了する、という飛び入り参加の前提と矛盾する挙動が起こりうる。

**`Defeated` プレイヤーの拘束（決定事項）**: 1.1の単一セッション制約により、`Defeated` のプレイヤーは以下のいずれかが起きるまで他チャンネルの戦闘に参加できない。

- 誰かが敵を倒す（`PlayerVictory`）
- 敵が全員逃走する（`EnemyEscaped`）
- 自ら `/escape` する（報酬を放棄することになる）
- チャンネルが消失する（`ChannelMissing`）

`Escaped` になった時点でこの拘束は解除される（同じ戦闘には再参加できないため、拘束を続ける理由がない）。この非対称は意図したものであり、「唯一の能動的な脱出手段が、報酬を放棄する `/escape` である」という点で、Escapeを安全弁と位置づけた設計思想と一致する。

### 4.4 TPシステム（決定事項）

スキルの行動コスト制は、MP消費でもクールダウンでもなく、**TPゲージ制**を採用する。

| 項目 | 値 |
|---|---|
| 範囲 | 0〜1000（上限超過分はカット） |
| 消費 | スキル発動時に`require_tp`分を消費 |
| 蓄積：通常攻撃 | +100（Attackモーションの再生を契機とする。下記参照） |
| 蓄積：防御 | +100（Defendモーション＝DRR付与モーションの再生を契機とする。下記参照） |
| 蓄積：被攻撃 | +floor(500 × 被ダメージ ÷ 最大HP)。ライブ攻撃・`SlipDamage` の両方に一律適用（下記参照） |

**TP蓄積の契機はモーションの再生（決定事項）**: 通常攻撃(+100)・防御(+100)は、`ActionType` や `skill_key` の選択時点ではなく、**AttackモーションまたはDefendモーションが実際に再生された時点**を契機とする。ここでいう「再生された」とは、モーション再生の5ステップ（4.2参照）のうち対象状態判定と命中判定を通過し、効果適用（ステップ5）に到達したことを指す。これにより、敵スキル選択（4.2参照）における「登録された通常攻撃」と「フォールバックの通常攻撃」の両経路が同一の1点に合流し、どちらのAttackかを判定する分岐が不要になる。この契機に使うAttack/Defendの `skill_key` はアプリ側定数として1箇所に集約する（TP契機・習得管理除外（23番対象外）・`Priority` 既定値の3者が同じ定数を参照する。11.3参照）。

**命中失敗時のTP（A-6・決定事項）**: 攻撃・回復モーションが `accuracy_rate` の命中判定を外した場合、そのモーションはスキップされ効果適用に到達しない（4.2 ステップ4・5.1参照）。したがってAttackモーションが外れれば +100 は発生せず、Defendモーション（DRR付与）が外れればDRR付与も +100 も発生しない。「再生されなかったものはTPを生まない」という単一の規則で閉じる。ただし相手の反撃を受ければ被攻撃TPは通常通り蓄積する（命中失敗はターン内の一事象であって行動の不成立ではないため）。

**Attack／Defend の `accuracy_rate` は 10000 固定とする（運用制約）**: 上記の帰結として Defend も確率で空振りしうるが、Defendは「TPが尽きたときの安全な選択肢」であるため、確率で無効化されるべきではない。回復モーションを含むスキルの `require_tp ≥ 200` と同じ節の運用制約として、Attack・Defend の `accuracy_rate` は 10000（100%）に固定する。両者の `skill_key` はアプリ側定数に集約されるため、制約の置き場所も確保されている。

**行動不能（`DisableMove`）時のTP（A-7・決定事項）**: 行動不能が成立してスキルのモーション再生がスキップされた場合も、TP蓄積は「モーション再生への到達」という単一契機で決まる。すなわち行動不能側はAttack/Defendの +100 を得ない（モーション再生という契機が来ないため）が、相手の反撃を受ければ被攻撃TPは通常通り蓄積する。行動不能はTP契機に特別扱いを設けない（詳細は5.4参照）。

**被攻撃TPの `被ダメージ` の定義（決定事項）**: `被ダメージ` は**台帳計上値＝実効ダメージ**（`min(パイプラインの最終ダメージ, 適用直前の現在HP)`、6.2参照）を指す。ライブ攻撃・`SlipDamage` のいずれで受けたダメージでも同一の定義を用いる。与ダメージ帰属（6.2）・被攻撃TP蓄積・報酬ゲート（6.2）の三者が、この単一の実効ダメージを共通の基準量とする。

**`SlipDamage` の被攻撃TP（決定事項）**: `SlipDamage` による被弾でもTPを蓄積する。蓄積は**インスタンス単位**で行い、各 `SlipDamage` インスタンスの実効ダメージについて `floor(500 × 被ダメージ ÷ 最大HP)` を加算する。併存する微小な `SlipDamage` が各回0に落ちて蓄積されないことは、実用上の許容誤差として意図的である。

**TPの主体と自滅の扱い（決定事項）**: 被攻撃TPは**被弾側**（HPを削られた対象）のTPに蓄積する。`auto` 付与の自滅 `SlipDamage`（「6行動で自滅する敵」等、`granter_entity_id = 自身`）では、与ダメージ計上と被弾が同一エンティティになるため、**自分の自滅ダメージで自分のTPが蓄積される**。これは意図した挙動である。

**保持場所**: 上記の蓄積量（100/100/500）は実質固定値に近く、DBマスタ側で人力調整するメリットが薄いため、C#側の定数として保持する。上限値1000も同様にシステム定数として扱う。

**なぜアプリ側定数なのか**: 装備効果の効果量のようにバランス調整で頻繁に変わりうる数値とは性質が異なり、この3値は実質固定値として扱ってよいと判断されたため。

**発生タイミング**: 「どのタイミングで蓄積するか」はダメージ計算ロジックの前後（攻撃前・攻撃後）に相当するフック式として実装する。

**現在値の永続化（決定事項）**: 参加者ごとの現在のTP値は `chido_battle_participant.current_tp` に保持される。**プレイヤーはセッション参加時に0で初期化される。敵は出現時に `chido_enemy_master.initial_tp` の値で初期化される**（4.2参照）。この初期値の非対称（プレイヤーは常に0固定）は現時点では拡張として据え置く。初期TP0の敵は初手で `require_tp > 0` のスキルを撃てないため、初手から特定のスキルを撃たせたい敵には `initial_tp` にその分の初期値を持たせる。

**回復モーションを含むスキルの `require_tp` の下限（決定事項・運用制約）**: 回復モーションを含むスキルの `require_tp` は **200以上**とする。

スキル発動自体はTPを生まない（蓄積するのは通常攻撃・防御・被攻撃のみ）ため、回復スキルを撃ち続けた場合のTP収入は被反撃分のみになる。同格の敵（`E = L`・Shape 1・強さ倍率 1・装備なし）では反撃が `4L`、最大HPが `12L` であるため、被反撃1回あたりのTPは `500 × 4L ÷ 12L ≈ 166.7` である。`require_tp ≤ 166` では回復を毎ターン撃ててしまい、5.1 に示す回復威力の実用帯（下限50% / 上限は `require_tp` 依存の「不死ライン」）が消滅する。

**今後の拡張の方向性（未設計）**: (a) 固定値そのものへの%補正、(b) 新規フック（例: 毎ターン蓄積などリジェネ的な仕組み）の追加。この3値自体を直接変更するのではなく、上記いずれかの形で拡張する想定。

## 5. ダメージ計算

### 5.1 計算パイプライン（3本化・決定事項）

**攻撃・回復・スリップの3本に分割する（決定事項）**。かつては攻撃と回復を1本のパイプラインで共有し、回復側で属性・クリティカル・被防御係数を「登録しない例外」として扱っていたが、例外処理のメンテナンスコストが共通化による負担軽減を上回るため、パイプラインそのものを分ける。3本の数値関係（回復＝被防御係数1の攻撃 等）は較正上の等価性として保たれる（後述）。

**共通の入力（有効ATK／有効DEF）**: いずれのパイプラインも、入力となる有効ATK・有効DEFは **2.3 の戦闘時ステータス**（`基礎 × 強さ倍率 × 装備補正 × 状態変化補正`、`StatusModifier` 込み）である。すなわち `StatusModifier` によるバフ・デバフは有効ATK／有効DEFに**既に織り込まれており**、パイプライン内で再適用しない（PreDefenseの二重適用を避けるための切り分け）。

#### 攻撃パイプライン

```
1. PreDefense フェーズ  … 属性補正のみ（有効ATK × 1.3^x、5.3参照）
2. 基礎ダメージ =
     - 有効ATK' + DEF = 0 の場合 → 0
     - それ以外の場合          → max(0, 有効ATK'² ÷ (有効ATK' + DEF))     （有効ATK' = PreDefense適用後）
3. PostDefense フェーズ … power（×power ÷100）× クリティカル（5.2）× DRR係数（(10000 − Σr) ÷ 10000、下記）
4. Flat フェーズ        … 固定加算/減算（現時点でデータ供給源を持たず常に恒等。下記）
5. Final フェーズ       … クランプ
6. 最低ダメージ 1 を保証
```

`IDamageModifier` の実装を積み上げるプラグイン型パイプラインになっており、フェーズごとに複数のModifierを連鎖適用できる。

**命中失敗はパイプラインに入らない（A-6・決定事項）**: `accuracy_rate` の命中判定を外したモーションは、ダメージ0・回復量0を計算結果として通すのではなく、そもそもパイプラインに入らない（4.2 ステップ4でスキップされる）。したがって命中失敗は「最低ダメージ1」の保証にも到達せず、TP契機（4.4）も発火しない。回復も同様に、外れれば回復量0ではなく再生そのものが起きない。

**PreDefense は属性補正のみ（決定事項）**: PreDefenseフェーズで有効ATKに乗るのは属性補正 `1.3^x`（5.3参照）**のみ**である。`StatusModifier` によるバフ・デバフは上述の通り有効ATKに織り込み済みのため、ここには含めない。

**基礎値の算出式（決定事項）**: 単純減算 `ATK - DEF` ではなく、比率式 `ATK'² ÷ (ATK' + DEF)` を用いる。

- `max(0, ...)` のクランプは維持する。新式は `ATK', DEF ≥ 0` であれば常に非負になるが、DEFが負値を取りうるため安全策として残す。負値を取る経路は、2.3 で確定したレイヤー内加算により強力なデバフが累積した場合である。
- `有効ATK' + DEF = 0` のゼロ除算ケースは、計算自体を発生させず基礎ダメージを0とする。その後 `max(0, ...)` を経て6段階目の「最低ダメージ1を保証」が適用されるため、最終ダメージは1になる。
- 5.3の属性倍率は攻撃者のATKに乗算されてからこの基礎値計算に入るため、新式では属性倍率がATKごと2乗される形になり、有利/不利の実質的な影響度が非線形に拡大する。これは意図した挙動である。厳密には2乗ではなく、`DEF ≫ ATK` のとき2乗へ、`DEF ≪ ATK` のとき1乗へ漸近する（「2乗される」は高DEF側の近似）。**属性の影響度は相手の硬さに依存して変動する**、というのが正確な挙動であり、これも意図した性質である。

**ダメージ軽減率（DamageResistRate・DRR、決定事項）**: 防御（Defend、4.2参照）は、DEFへの補正ではなく、最終ダメージへの乗算係数 `(1 − DRR)` として表現する。

- **理由**: DEF補正で防御を表現すると、数値インフレによりDEFの絶対値が膨張するにつれ「DEF+○%」の意味が変わり、防御が陳腐化する。`(1 − DRR)` は常に同じ割合だけダメージを削るため、インフレに対して意味が一定に保たれる。これは `power` を Time To Kill 尺度の一次元量とした判断（後述）と同じ論理である。
- **保持形式**: DRRは状態変化 `StatusModifier` の一種として表現する（5.4参照）。permyriad 符号あり。「装備でしか動かないpermyriad」であるLuckに対し、DRRは「状態変化でしか動かないpermyriad」とみなせる。
- **合成（加算）**: 複数のDRRが併存する場合、`Σr`（各インスタンスの `rate` の合計）で加算合成し、係数 `(10000 − Σr) ÷ 10000` を基礎ダメージに乗じる。この係数は**途中でクランプしない**（`Σr > 10000` なら係数が負になり基礎ダメージが負に振れるが、最終の「最低ダメージ1」がこれを吸収する）。DRR 50%×2でダメージ1、×3でも下限1で止まり、回復への反転は起きない。
- **適用対象**: DRRは**攻撃モーション由来のダメージにのみ**登録する。回復・`SlipDamage` には登録しない。

**Flat フェーズ（決定事項）**: フェーズ自体は残置するが、現時点でデータ供給源をスキーマ上に持たず、常に恒等（加算0）で通過する。防御貫通率と異なりフェーズを廃止しないのは、将来の固定加減算のための拡張余地として残すためである。

**このパイプラインは「最終ダメージ」しかクランプしない**。適用先である現在HPは `MaxLife` を超えうるし、下限は戦闘不能（0）である。

#### 回復パイプライン

```
回復量 = floor(有効ATK × power ÷ 100)     （下限0）
```

- 有効ATKは2.3の戦闘時ステータス（`StatusModifier` 込み）。参照する物理/魔法は攻撃時と同じく `attack_type` で選択する。
- **属性補正（5.3）・クリティカル（5.2）・対象DEF・DRRのいずれも適用しない**。回復は「防御されない攻撃」であり突き合わせる相手が味方であるため、対象DEFを参照しない（適用すると「硬い味方ほど回復しづらい」という直感に反する）。対象の最大HP基準も採らない（回復量が術者のレベル・装備から独立し、2.3の原則の外に飛び出すため）。
- **下限は0**（攻撃・スリップの「最低1」とは異なり、丸めで0になる回復は0のままとする）。

#### スリップパイプライン（SlipDamage）

```
1. PreDefense フェーズ  … 属性補正のみ（スナップショットATK × 1.3^x）
2. 基礎ダメージ         … スナップショットATK' と、attack_type で選んだ対象DEF で攻撃式と同型
3. PostDefense フェーズ … power（×power ÷100）のみ
4. Final / 最低ダメージ 1
```

- 使用するATKは付与時点のスナップショット（`chido_effect_slip_damage_instance.status_attack_value`）であり、これは付与者の付与時 `StatusModifier` を既に織り込んでいる。PreDefenseが属性のみであるため、二重適用は起こらない。
- **クリティカルなし・DRRなし**（Modifierを登録しない）。最低ダメージは1。詳細は5.4参照。

#### 較正上の等価性（旧「回復＝防御されない攻撃」）

パイプラインを3本に分けたことで、攻撃と回復は実装を共有しないが、**数値関係は保たれる**。基礎ダメージ式は `ATK² ÷ (ATK + DEF) = ATK × [ ATK ÷ (ATK + DEF) ]` と書き換えられ、`ATK ÷ (ATK + DEF)` を**被防御係数**と呼ぶなら、両者は同じ形をしている。

```
ダメージ = 攻撃力 × 威力 × 被防御係数
回復量   = 攻撃力 × 威力                 ← 被防御係数 = 1 と等価
```

被防御係数は `DEF = ATK` のとき 0.5、`DEF → 0` で 1、`DEF → ∞` で 0 に漸近する。プレイヤーも敵も 2.3 の Scale が ATK・DEF ともに 8 のため、同格（`E = L`・Shape 1・強さ倍率 1・装備なし）では**ちょうど 0.5** になる。これは実装の共有ではなく**バランス較正の根拠**であり、後述の換算則（等価な回復威力 = 攻撃威力 × 被防御係数）を導く数値上の等価性として引き続き有効である。

#### 丸め規則（決定事項）

**すべての除算は `floor`（0方向ではなく負の無限大方向の切り捨て）とし、各フェーズ境界で整数へ床る**。BigInteger の整数除算は0方向切り捨てであり、負値では `floor` と結果が異なりうるため、負のオペランドを扱う実装では明示的に `floor` 方向へ寄せる（負ダメージは最終の「最低ダメージ1」が吸収するため最終結果は不変だが、中間値の期待値を一意にするために宣言する）。

除算が入る点は以下であり、それぞれが独立した床除算点になる。

- PreDefense: 属性補正 `× 13^x ÷ 10^x`（`x ≥ 0`）／ `× 10^|x| ÷ 13^|x|`（`x < 0`、分母分子を入れ替える。5.3参照）
- 基礎ダメージ: `÷ (有効ATK' + DEF)`
- PostDefense: `power`（`× power ÷ 100`）／ DRR（`× (10000 − Σr) ÷ 10000`）／ クリティカル係数
- 回復: `× power ÷ 100`

**防御貫通率の廃止（決定事項）**: かつてパイプラインの1段目に `有効防御力 = DEF × (1 - 防御貫通率)` が存在したが、**廃止する**。理由は3点。

1. **データ供給源がスキーマ上に一切存在しなかった**。値の型も既定値もどのレイヤーが与えるかも定義されておらず、「設計された未実装機能」ではなく実装済みコードの構造が写経されたものである可能性が高い。1.3 の `BigInteger` と同種の「名残」として扱う
2. **威力の一次元性を壊す**。後述の通り `power` は Time To Kill 尺度の一次元量であり、防御貫通率が同居すると「威力200%と防御貫通50%のどちらが強いか」が DEF に依存して変わり、比較尺度でなくなる
3. **冗長である**。「対象のDEFを一時的に無効化する」機能は `StatusModifier` による DEF デバフで表現可能であり（5.4参照）、新たな機構を増やす必要がない

廃止に伴い「有効防御力」という語も消える。`有効DEF` が `DEF` と異なる値になる経路が防御貫通率だけだったためである（`有効ATK` は `PreDefense` フェーズという明確な加工元があるため残す）。

**DEFへの対抗手段（決定事項）**: 廃止の帰結として、高DEFの敵に対して取りうる手段は以下の3つに限定される。いずれも既存の機構であり、新しい概念を導入せずに設計が完結する。

1. 攻撃力を上げる（レベル・装備）
2. 相手のDEFを下げる（`StatusModifier` デバフ、5.4参照）
3. 属性有利を取る（5.3参照。上述の通り高DEF相手ほど属性の影響が大きくなる）

#### `power`（威力）の意味論と較正（決定事項）

**`power` は Time To Kill 尺度の一次元量であり、「通常攻撃を1としたときの強さ」を表す。** ゲームバランスの調整は装備側の数値で行い、威力には他の軸を同居させない。この一次元性があるからこそ、以下の換算則が成立する。

```
等価な回復威力 = 攻撃威力 × 被防御係数 = 攻撃威力 × ATK ÷ (ATK + DEF)
```

同格なら 1/2 倍。すなわち**通常攻撃（威力100%）と釣り合う回復モーションの威力は 50%** であり、これが数値調整の起点となる。

| | 威力100%のとき | 最大HP(12L)比 |
|---|---|---|
| 通常攻撃 | 4L ダメージ | 33.3% |
| 回復 | 8L 回復 | 66.7% |

**回復威力の実用帯（決定事項・運用指針）**

- **下限は 50%**（TPと無関係）。4.2 の通り Skill も反撃を受けるため、自己回復のターンも反撃を食らう。同格では反撃 `4L` に対し回復 `8L × 威力` であり、威力50%未満の回復は「そのターンに通常攻撃したほうがマシ」になる。威力50%ちょうどは回復量＝反撃量で何も起きない点である
- **上限は `require_tp` が決める「不死ライン」**。スキル発動自体はTPを生まないため（4.4参照）、「通常攻撃を n 回して回復を1回撃つ」サイクルのHP収支がプラスに転じる威力を超えると、そのプレイヤーは同格の敵に対して絶対に死ななくなる

| `require_tp` | 回復1回あたりに要する通常攻撃ターン数 | 不死になる威力 | 実用帯 |
|---|---|---|---|
| 100 | 0（毎ターン撃てる） | 50% | **なし（威力50%超で即不死）** |
| 167〜400 | 1 | 100% | 50% 〜 100% |
| 500〜600 | 2 | 150% | 50% 〜 150% |
| 800 | 3 | 200% | 50% 〜 200% |
| 1000 | 4 | 250% | 50% 〜 250% |

`require_tp ≤ 166` の回復スキルは威力をどう設定しても破綻するため、4.4 で下限を 200 と定めている。安全側の目安としては実用帯の中央（`require_tp = 500` なら威力 75〜100% 程度）から始めるのが妥当。

不死ラインは「同格の敵に対して」である。格上（`E > L`）が相手なら反撃が重くなるため不死ラインは上がり、回復の存在意義は「格上に勝てるようになること」に収束する。装備なしの素の勝敗分水嶺は `E ≤ L` である（後述）ため、**回復モーションはこの分水嶺を押し上げる唯一の手段**という位置づけになる。これは 6.2 の「支援特化には自己強化といった、何らかの形で敵にダメージを与えられる選択肢を用意する」という方針とも噛み合う。

#### 勝敗の分水嶺（参考）

2.3 のステータスはレベルに完全に線形（HP = 12L、ATK = DEF = 8L、Shape 1・強さ倍率 1・装備なし）であるため、新式を通すと次が得られる。

- プレイヤーが敵を倒すのに要するターン数 = `1.5 × E × (L + E) ÷ L²`
- プレイヤーが倒されるまでのターン数     = `1.5 × L × (L + E) ÷ E²`

両者を比較すると `E³ ≤ L³`、すなわち**基準ケースでは「敵レベル ≤ 自レベル」が勝敗の分水嶺**になる（4.1 の反撃モデル＝1行動につき1反撃を前提）。この値は 6.2 の経験値按分と 10.1 の敵レベル進行の設計根拠として参照される。

### 5.2 クリティカル（決定事項）

| 項目 | 値 |
|---|---|
| 発生率 | 4%（ポケモンの通常クリティカル率に近い水準） |
| 倍率 | ×1.5 |
| 適用フェーズ | `PostDefense`（最終ダメージへの乗算） |

既存の `RatioMultiplierModifier.Critical` ファクトリは元々 `PostDefense` フェーズで実装済みであり、この決定と**そのまま合致**している。発生判定（4%の乱数抽選）自体は `IBattleAction.ExecuteAsync` に渡される `Random rng` を使って行動側実装が担う想定（未実装）。

**回復モーションには適用しない（決定事項）**: クリティカルの適用対象は上表の通り「最終ダメージへの乗算」であり、回復量は最終ダメージではない（5.1参照）。「会心の回復」は認めない。

### 5.3 属性（決定事項）

- 種類（10種、固定）: 火 / 水 / 草 / 土(大地) / 空(飛行) / 雷 / 氷 / 光 / 闇 / 無(Neutral)
- 適用対象: **攻撃者の攻撃力（ATK）に乗算** → 防御差し引き**前**の `PreDefense` フェーズで処理する。

**補正式（決定事項）**: 式は1本しかない。属性の数によって分岐しない。

```
属性補正倍率 = 1.3 ^ x
x = Σ(a ∈ モーション属性) Σ(d ∈ 実効属性) rel(a, d)      … 総当たりペアの合計
rel(a, d) = 有利 +1 / 不利 −1 / 等倍 0
```

参考値として `x = +1 → ×1.3`、`x = -1 → ×1.3⁻¹ ≒ 0.769`。

**単一属性も属性なしも、この式の特殊ケースにすぎない。** 単一属性同士なら `x ∈ {-1, 0, +1}`。`elements = 0` は総当たりの対象集合が空になるため `x = 0`、`1.3^0 = 1.0` となり、2.4 の「属性相性計算自体が省略される」と結果が一致する（＝あの省略は実装上の最適化であって仕様上の分岐ではない）。`Neutral` を含む集合が、`Neutral` を除いた集合と常に同じ `x` を返すことも、後述の相性表の制約から従う。

**相性表（決定事項）**

行が攻撃側（モーション属性）、列が防御側（実効属性）。`○` = 有利（+1）、`×` = 不利（−1）、`－` = 等倍（0）。

| 攻撃＼防御 | 火 | 水 | 草 | 土 | 空 | 雷 | 氷 | 光 | 闇 | 無 |
|---|---|---|---|---|---|---|---|---|---|---|
| 火 | － | × | ○ | × | × | － | ○ | － | ○ | － |
| 水 | ○ | － | × | ○ | ○ | × | × | － | － | － |
| 草 | × | ○ | － | ○ | × | ○ | × | － | × | － |
| 土 | ○ | × | × | － | × | ○ | ○ | ○ | － | － |
| 空 | ○ | × | ○ | ○ | － | × | × | － | × | － |
| 雷 | － | ○ | × | × | ○ | － | × | － | － | － |
| 氷 | × | ○ | ○ | × | ○ | ○ | － | × | － | － |
| 光 | － | － | － | × | － | － | ○ | － | ○ | － |
| 闇 | × | － | ○ | － | ○ | － | － | × | － | － |
| 無 | － | － | － | － | － | － | － | － | － | － |

**相性表の不変条件（決定事項）**

1. **完全反対称**: 全45ペアが `(○, ×)` か `(－, －)` のいずれかである。「相互に有利」「片方だけ有利で逆は等倍」の組み合わせは存在しない。データの実体は上三角45要素で足り、単体テストで `rel[a,b] == -rel[b,a]` を強制できる。プレイヤーから見ても「その敵に有利なら、その敵からも有利を取られない」という直感が保証される
2. **`Neutral` の行・列はすべて `－`（等倍）**: 2.4 の通り `elements = 0` は等倍になるため、`Neutral` 単体との等価性を保つために必要
3. **対角はすべて `－`**: 同属性同士は等倍

**保持場所（決定事項）**: 相性表は **C#側の定数**として保持する。DBマスタ（`chido_element_affinity_master` 等）は**新設しない**。

**なぜDBマスタにしないのか**: 属性は `[Flags] enum Element` としてC#側に存在する。相性表をDBに置くと、属性の定義（C#のenum）と属性の関係（DBの行）が二重管理になる。そして属性を追加する際は enum への値追加＝再コンパイル＝再デプロイが必須であるため、**DB化しても「再デプロイなしに変更できる」という唯一の実利が得られない**。得られるものがないまま、(a) マスタ行の欠損・反対称性の破れという実行時エラーの新カテゴリとその検査コード、(b) 100行のマスタを引くクエリまたはキャッシュ層と無効化の設計、(c) enum の値とマスタのキーの対応を維持する責務、が増えるだけになる。

DBマスタが適するのは「enum の変更を伴わずに数値だけを頻繁に触るもの」（敵のステータス係数、ドロップ率、抽選重み等）であり、相性表はこれに該当しない。これはゲームルールの構造そのものであって、バランス調整用のパラメータではない。

**実装形式**: 10×10のリテラル（上表と同じ並び）を静的テーブルとして持ち、不変条件は単体テストで守る。`x` の算出は、行ごとに「有利な防御属性のビットマスク」「不利な防御属性のビットマスク」へ前計算しておけば `popcount` 2回で済み、`x = Σ_a (popcount(Adv[a] & defender) − popcount(Dis[a] & defender))` となって仕様文の直訳になる。

**攻撃側・防御側の属性の解決**: 攻撃側は**攻撃モーションのモーション属性**を、防御側は**実効属性**（本体 ∪ 装備 ∪ 一時付与、2.4参照）を用いる。属性相性は攻撃モーションでのみ計算される（回復・状態変化付与・解除・戦闘離脱はモーション属性そのものを持たない）。

**スキル属性とモーション属性の区分（決定事項）**

属性は「スキル属性」と「モーション属性」の2つに明確に分離される。

| 区分 | 対応データ | 役割 |
|---|---|---|
| モーション属性 | `chido_skill_motion_attack_master.elements` | ダメージ計算時に実際に参照され、対象との相性判定に使用される実効値。**攻撃モーションのみが持つ**（回復・状態変化付与・解除・戦闘離脱は属性を持たない） |
| スキル属性 | `chido_skill_master.elements` | ダメージ計算には一切使用しない、いわば"見せかけ"の値。スキル全体の属性をUI等で大まかに示すための表示専用データ。回復スキル等、攻撃モーションを持たないスキルでも保持できる |

**なぜ分離するのか**: モーション属性からスキル属性を自動算出する方式だと、複数モーションを持つスキルで属性がばらつく場合に不自然になる。例えば「自分を強化（無属性）」→「火属性の攻撃」という2モーション構成のスキルでは、モーション属性を単純合算すると「火・無」になってしまうが、これはスキル全体の属性表現として直感に反する。スキル属性を独立した手動設定値にすることで、この問題を回避する。

**手動設定の指針**: スキル属性は代表的な攻撃モーションの属性を踏襲するのが望ましい、という暗黙の了解はあるが、あくまで手動設定が前提であり、モーション属性からの自動導出ロジックは設けない。

**保持数のルール（目安）**

- エンティティの本体属性、スキル属性、モーション属性は、いずれも**最大2つまでを目安とする**。ただしこれはバリデーションで強制する類の制約ではなく、計算負荷・ゲームバランスの両面から妥当と考える目安であり、データ構造上は3つ以上を保持することも技術的に可能なままにしておく。
- 装備由来の属性（2.4）は最大5スロット分の OR となりうるため、実効属性は上記の目安を超えうる。`1.3^x` の `x` の振れ幅がその分広がる点は検討済みであり、下記の通り許容する。

**`x` の到達範囲と、その許容判断（決定事項）**

**防御側の属性は増えても希釈されず、振れ幅を増幅する**（各ペアが加算されるため）。上記の相性表における `x` の到達範囲は以下。

| 条件 | `x` の範囲 | ATKへの倍率 |
|---|---|---|
| 攻撃1属性 × 防御≤5属性 | −4 〜 +4 | 0.350 〜 2.856 |
| 攻撃2属性 × 防御≤5属性 | −6 〜 +6 | 0.207 〜 4.827 |

さらに 5.1 の新式を通ると最終ダメージでは非線形に拡大し、`DEF = ATK` の場合で最大／最小が約112倍の開きになる。

**これを許容する。** `x` をクランプする案（例: `-2 ≤ x ≤ +2`）はクランプ境界で属性を足す意味が消える死に領域を生み、攻撃側属性数で除算する案は防御側の膨張に効かず `1.3^x` の直感も失われる。いずれも「属性を持つほど強い/弱い」という関係を歪め、本節が「最大2つまでを目安」を**バリデーションで強制しない**としている設計思想（データ側の自由度は残し、バランスは運用で取る）と整合しない。

振れ幅が問題化するのは「属性付き装備を5スロット揃える」ような極端なケースであり、これは 2.4 が「大半の装備は `0` を設定する」という運用前提を置くことで既に回避されている。**制約はスキーマではなくマスタデータの入れ方で担保する**、という既存方針の延長線上にある。通常プレイの範囲（`|x| ≤ 2`）では 0.44〜2.12 倍程度に収まる。
- 状態変化による「後天的・一時的な属性付与」には上限を設けない（5.4参照）。
- 属性種類が10種で今後増える予定がないため、データ表現は `[Flags] enum`（ビットフラグ）で十分。

**将来拡張の方向性（未設計）**: 「モーションに反応する効果」（例: 攻撃モーション実行時にHPを回復する等）の拡張が考えられる。当初は「モーション属性に反応する効果」として構想していたが、11.2-8 の決定（属性は攻撃モーションのみが持つ）に伴い方針を変更し、**「モーション属性」への反応は不要**とした。反応の契機はモーションそのもの（種別・実行の有無等）に置く。現時点では方向性のみで詳細は未設計（5.4・11.4参照）。

> **⚠ 実装上の要修正点**: 現在の `RatioMultiplierModifier.Elemental` ファクトリは `ModifierPhase.PostDefense` にハードコードされているが、今回の決定（属性補正は攻撃者ATKへの乗算＝`PreDefense`）とは異なる。また `AttackType`（現状 Physical/Magical の単純enum）とは別に、属性は複数保持を前提とした `[Flags] enum Element` として新設する必要がある。既存コードとの差分として要対応。加えて、ダメージ計算時に参照すべきはモーション属性（攻撃モーションのみが持ち、`chido_skill_motion_attack_master.elements` に格納される）であり、スキル属性は参照しない点に注意。5.1 の通りパイプラインは攻撃・回復・スリップの3本に分割され、属性補正（Elemental Modifier）は**攻撃パイプラインとスリップパイプラインの `PreDefense` にのみ**登録する（回復パイプラインには登録しない。回復モーションはモーション属性を持たない）。スリップパイプラインが参照する属性は `chido_effect_slip_damage_master.elements` であり、攻撃モーションの `elements` とは別系統である。

### 5.4 StatusEffect（決定事項）

`IEntity` または `BattleParticipant` に、発生源・付与属性・持続条件を持つ `StatusEffect` 相当のリストを追加し、ダメージ計算時に「本体属性 ∪ 装備属性 ∪ 一時付与属性」を集計してから相性判定にかける。

**マスタ側の構造（確定）**: 状態変化は以下の4種に分類され、それぞれ専用のサブテーブルを持つ。

| 種別 | 内容 |
|---|---|
| `StatusModifier` | ステータス変動（%補正）。**ダメージ軽減率（DRR）を含む**（下記） |
| `SlipDamage` | 継続ダメージ |
| `DisableMove` | 行動不能 |
| `ElementGrant` | 一時的な属性付与 |

**ダメージ軽減率（DRR）は `StatusModifier` に編入する（決定事項）**: 防御（Defend、4.2参照）が付与する「ダメージ軽減率」は、新規のサブタイプを設けず、`StatusModifier` の対象ステータス（`target_status`）の一値として表現する。permyriad 符号あり。DRRは「状態変化でしか動かないpermyriad」であり、「装備でしか動かないpermyriad」であるLuckと対をなす。

- **既存の `StatusModifier` との意味論の違い**: 既存の `target_status`（HP/物理攻撃/物理防御/魔法攻撃/魔法防御）は、レイヤー内で `+%` 加算した結果を **2.3 の状態変化補正倍率**（`1 + Σr`）として乗算レイヤーに供給する。一方DRRは、同じ `rate` 列に `+%` 加算で溜めるが、その**加算結果そのもの**（`Σr`）を `(10000 − Σr) ÷ 10000` の形で 5.1 の PostDefense に供給する。すなわち **DRR行は 2.3 の乗算レイヤーには一切入らない**。同じインスタンス側 `rate` を読みながら、`target_status` がDRRを指す行だけ合成の意味が異なる、という分岐がアプリ側に生まれる。これは許容する（超厳密には意味論が一意でないが、`target_status` による分岐で十分）。
- **Defendの表現**: Defendの軽減率50%は固定値であるため、`chido_effect_status_modifier_master.fixed_rate = 5000` の固定値行として持てる（インスタンス側テーブルを要しない。DRRという性質は不定値も許容するが、Defendという具体的スキルは固定値表現でよい）。
- **合成と下限**: 併存時は `Σrate` で加算合成し、係数を途中でクランプせず、最終ダメージの「最低1」で吸収する（5.1参照）。
- **適用対象**: DRRは攻撃モーション由来のダメージにのみ乗る。回復・`SlipDamage` には乗らない（5.1参照）。

**一時的な属性付与の扱い（決定事項）**: モーション属性に反応する形での「一時的な属性付与」（5.3参照）は、上記のうち他の3種のいずれとも性質が異なる（%補正ではなくビット加算のため）。既存のステータス変動用テーブルに混在させず、専用のマスタを新設して表現する（`chido_effect_element_grant_master`）。

**持続条件（決定事項）**: 持続条件は「**残り有効行動数**」によるカウントダウン方式を採用する。該当ターン（1.2参照）に**関与した**エンティティの行動がすべて終了した直後、ターン終了の直前に残り有効行動数を-1し、0に達した時点で状態変化は消失する。

**減衰の対象＝関与者集合（A-8・決定事項）**: 「関与したエンティティ」は、ターン開始時（行動が受理され、反撃者が確定した時点）に固定される **行動者と反撃者（`CurrentTarget`）の2エンティティ**である。現行のターンモデルでは行動者は常にプレイヤー、反撃者は常に敵であるため、集合の内訳は「プレイヤー1体＋敵1体」に固定される。

- **集合外は減衰しない**: `Use`・味方対象モーションで効果を受けた第三者、組の他の敵、同チャンネルの他プレイヤーは減衰しない。味方に付与したバフは、その味方自身が行動するまで `remaining_actions` を保つ（弾は撃つから減る、という比喩と一貫する）。
- **減衰の適用範囲**: 集合内の各エンティティが保持する全効果インスタンス（`chido_battle_effect` + `chido_player_effect` の両スコープ、`remaining_actions IS NOT NULL` のもの）を -1 する。実装上は `chido_battle_effect` を `WHERE entity_id IN (行動者, 反撃者)`、`chido_player_effect` を `WHERE user_id = 行動者`（敵は本テーブルに行を持たない）で閉じる。
- **集合の不変性**: ターン中の `Defeated`／`Escaped` 化、行動キャンセル、モーション中断、命中失敗、行動不能（`DisableMove`）成立は、いずれも集合を変えない。
- **`Use` 等で受動的に影響を受けたプレイヤー**は関与者ではなく、減衰しない。
- **行動が不成立に終わった場合はターンが開かず、減衰も起きない**。該当するのは (a) 単一セッション制約による拒否（1.1）、(b) `[対象]` の対象解決失敗（`Defeated`／`Escaped` 指定、4.2参照）、(c) `/escape` コマンド（4.2 の通りターンを消費しない）。一方**離脱モーション**（`motion_type = 3`）はスキル再生＝ターンであるため、成功・失敗を問わず双方が減衰する。

**「ターン」ではなく「残り有効行動数」である理由（決定事項）**: 減衰の契機は**時間の経過ではなく、保持者がターンに関与したこと**である。これは時計ではなくカウンタの消費であり、弾数が減るのは撃つからであって、放置している間に弾が減らないのは当たり前である。保持者にとって1ターンは自分の1行動そのものなので、数値としては「ターン数」と一致するが、**「ターン」という語は「戦闘内の時計」という誤った含意を持ち込む**。列名も `duration_actions` / `remaining_actions` とし、スキーマ・仕様書ともに正確な語を用いる。

なお `/escape`（4.2 の通りターンを消費しない）では減衰しない。ただし離脱**モーション**（`motion_type = 3`）ではターンが開くため、成功・失敗を問わず関与者集合の双方が減衰する（`/escape` とモーションの経路差による非対称）。ターン開始後に `Defeated` 化した参加者は、その時点で既に関与者集合に含まれていれば減衰する（「行動しないから減らない」のではなく「関与者集合に入らないから減らない」が正確な理由であり、結論は変わらない）。いずれも「残り有効行動数」および関与者集合の定義から自然に導かれる。

**表示上の「ターン」**: Discord埋め込みでは `[毒] (3)` のように表示するが（3.1参照）、これは保持者にとって「あと3回自分が行動したら切れる」を意味しており正確である。「行動数」という表現が一般的でないため、**UIの語としてのみ「ターン」に丸める**。

**初期値の出所（決定事項）**: 付与元ごとに可変とする。効果マスタ側で固定すると「弱い毒（2行動）／強い毒（8行動）」を別々の `effect_key` として量産することになり、サブテーブルまで丸ごと重複するため。付与元は2つあり、**両方が同じ列を持つ**（`effect_rate` について既に確立している対称性に従う）。

| 付与元 | `affect_reason` | 持続の出所 |
|---|---|---|
| `chido_skill_motion_effect_master`（状態変化付与モーション） | `skill` | `duration_actions` |
| `chido_enemy_effects_master`（戦闘開始時の敵への初期付与） | `auto` | `duration_actions` |

後者にも必要なのは、例えば「6行動で自滅する敵」を auto 付与の `SlipDamage` として表現する場合、持続の出所がモーション側ではなく auto 付与側になるためである（この敵の存在は 6.2 の貢献率の分母に下限を必要とさせる。6.2参照）。

**`NULL` の意味（決定事項）**: `NULL` = **無期限**（残り有効行動数という属性が適用されない）。これは Magic Value の濫用ではなく、SQLの三値論理の本来の用法であり、望ましい挙動が演算・比較の両方で自動的に得られる。

- デクリメント: `SET remaining_actions = remaining_actions - 1` は NULL 行に対して `NULL - 1 = NULL` を返す。除外条件なしで無期限効果は減らない
- 消失判定: `WHERE remaining_actions = 0` は NULL に対して UNKNOWN を返して一致しない。無期限効果は自動的に消失判定から漏れる

`-1` や `65535` を番兵にすると、両方に明示的な除外条件が必要になり、書き漏らしがバグになる。

**`0` は取らない**: 「付与した瞬間に消失する」となり意味を持たない（即時効果は攻撃・回復モーションが担うため、状態変化として表現する必要がない）。定義域は **NULL または1以上**。

**スコープと持続の関係（決定事項）**: 書き込み先は `entity_type` × `clear_on_battle_end` で決まり、`remaining_actions` とは独立である。

| `clear_on_battle_end` | `duration_actions` | 意味 | 終わりの保証 |
|---|---|---|---|
| 1 | NULL | この戦闘の間ずっと | 戦闘終了 |
| 1 | 有限 | この戦闘の中で N 行動 | 両方 |
| 0 | 有限 | **戦闘を跨いで N 行動** | 行動数 |
| 0 | NULL | **禁止**（真に永久） | **なし** |

> **不変条件**: すべての状態変化は、有限の行動数か、戦闘の終了か、そのいずれかによって必ず終わりが保証される。

**`clear_on_battle_end = 0` の効果を付与する場合、`duration_actions` は NOT NULL 必須**とする。テーブルをまたぐ条件のため CHECK 制約では表現できず、整合性の担保はアプリ側の責務。

**なぜ「戦闘を跨ぎつつ有限」なのか**: `clear_on_battle_end` というフラグは、その反対側（戦闘を跨ぐ状態変化）が存在してはじめて意味を持つ。そして残り有効行動数は戦闘の境界を何も参照しないため、「戦闘終了時に消さない」ことと「減衰を続ける」ことだけで、戦闘を跨ぐ有限の効果が新しい列なしで表現できる。

**なぜ「真に永久」を禁じるのか**: 真に永久なステータス補正は、レベルや装備や称号と同じ**プレイヤーの属性**であって、付与・解除というライフサイクルを持つインスタンスではない。それを状態変化として持つと、ライフサイクルの片側（解除）だけが永久に来ない歪んだ形になり、加算合成（2.3参照）される永続デバフが単調増加して上限なくステータスを蝕む。この禁止1つで、その暴走が構造的に閉じる。

**永続スコープの減衰の書き込み先（決定事項）**: `chido_player_effect` は戦闘中に**その場で**減衰させる。「戦闘開始時に `chido_battle_effect` へ複製し、終了時に書き戻す」という作業コピー方式は採らない。4.3 が「全参加者が戦闘不能でもセッションは終了しない」「セッションは非同期・長期間開きっぱなしになりうる」と定めている以上、**書き戻しの契機が来る保証がなく**、永続効果の真値が無期限に戦闘テーブルに人質に取られるためである。ロックについては 7.2 参照。

**DisableMove／SlipDamageの発動タイミング（決定事項）**:

- `DisableMove`（行動不能）は、対象が行動しようとした時点で判定する。
- `SlipDamage`（継続ダメージ）は、対象の行動枠の終了直後に発動する。4.2で確定した通り、Escapeを除く全ActionType（Attack/Skill/Defend/Use）はいずれもスキル発動に収束するため、この発動タイミングはActionTypeを問わず一律に適用できる。行動不能でモーション再生がスキップされた場合も、行動枠自体は開くため `SlipDamage` は発動する（下記A-7-j）。`/escape`（ターンを消費しない＝行動枠が開かない）では発動しない。

**行動不能（`DisableMove`）の判定内容（A-7・決定事項）**: 判定はエンティティごと・その行動の直前に1回行う。

- **確率**: `disable_rate`（permyriad）を毎回抽選し、成功したら行動不能とする（付与時に固定せず、行動しようとするたびに引く）。
- **成否によらず常に行われること**: (b) ターン消費、(c) TP蓄積（下記の読み替えに注意）、(d) 相手の反撃、(e) 残り有効行動数の減衰。行動不能の成否はこれら4項に影響しない。
- **成立時にスキップされるのは、そのエンティティのスキル1本ぶんのモーション再生のみ**。

**(c) の読み替え**: 「TP蓄積は常に行われる」は「+100 も付与する」という意味ではない。4.4 の通り +100 の契機は「Attack/Defendモーションの再生（＝効果適用への到達）」であり、行動不能ではモーションが再生されないため +100 は構造的に発生しない。相手の反撃を受ければ被攻撃TPは通常通り蓄積する。行動不能に特別扱いを設けない、という趣旨と一致する。

**(e) の帰結**: A-8 の関与者集合により、`DisableMove` を保持したまま行動不能になったエンティティも自身の `remaining_actions` を消費する。したがって「行動不能が永久に解けない」実装にはならない。

**行動不能の詳細規則（A-7-f〜j・決定事項）**:

| # | 論点 | 規則 |
|---|---|---|
| f | 併存する複数 `DisableMove` インスタンスの合成 | `instance_id` 昇順に各インスタンスで独立抽選し、**最初の成功で打ち切り**。`SlipDamage` の「各インスタンスがそれぞれ発動」「`instance_id` 順」に揃える。確率であるため `StatusModifier` の加算合成は適用しない |
| g | 行動不能時に `require_tp` を消費するか | **消費しない**（スキル発動そのものが起きていない。TPを取ると二重罰になる） |
| h | 敵が行動不能のとき `rotation_index` を進めるか | **進める**（4.2 の「敵が行動するたび」を「敵にターンが回るたび」と読む。進めないとローテが凍結し、解除後に同じスキルへ戻る） |
| i | 判定を行動順決定の前に行うか後に行うか | **後**。スキル抽選は通常通り行い、再生の直前に判定する（前に置くとスキルが確定せず `Priority` が読めず、1.2 の行動順決定が崩れる） |
| j | 行動不能時に `SlipDamage` が発動するか | **発動する**（契機を「そのエンティティの行動枠の終了直後」と読む。発動しないと、行動不能と毒を併せ持つ相手に対し毒が実質無効化される） |

**行動不能ターンの処理順（決定事項）**: 上記 i・j により、行動不能を含むターンは次の順で処理される。

```
1. 両者のスキル確定（敵は action_pattern_type で抽選、require_tp フォールバック含む）
2. Priority → Speed → Random で行動順決定
3. 先攻: DisableMove 判定 → 成立ならモーション再生をスキップ / 不成立なら再生
4. 先攻の SlipDamage 発動
5. 後攻: 同様（先攻の一撃で戦闘不能なら 4.1 によりキャンセル）
6. 後攻の SlipDamage 発動
7. 関与者集合（2体）の remaining_actions を -1 し、0 の行を削除（同一トランザクション）
```

**SlipDamageのダメージ算出（決定事項）**: 算出は攻撃モーションと同型であり、5.1 のスリップパイプラインを通す。

- **威力・属性**: `chido_effect_slip_damage_master.power`（威力、整数%）と `chido_effect_slip_damage_master.elements`（攻撃属性、ビット列）を用いる。攻撃側属性はマスタ由来のため付与後も不変であり、スナップショット対象ではない（マスタ参照ゆえ固定）。
- **攻撃力（ATK）**: 付与時点の術者のATK実値のスナップショット（`chido_effect_slip_damage_instance.status_attack_value`）を用いる。物理/魔法のどちらのATKを読むかは `attack_type`（下記）で決まる。
- **対象の防御力・属性相性は攻撃モーションと同じく考慮する**。最低ダメージは1。**クリティカルはしない**（攻撃モーションとの唯一の相違）。DRRも乗らない（5.1参照）。
- **スナップショットするのは付与時ATC・攻撃種別（`attack_type`）のみ（決定事項）**: 対象DEF・対象の実効属性・攻撃側属性は**発動時に取得**する。したがって「毒を受けた後に装備を変えて対象DEFを上げるとスリップが軽くなる」「属性相性は毎回発動時の対象状態で判定される」という挙動になり、これは意図的である。

**`attack_type` の出所（決定事項）**: `SlipDamage` の `attack_type`（物理/魔法）は、**それを付与した攻撃（付与モーション）によって動的に決まる**。同一の `effect_key`（例:「毒」）でも、物理スキルで付与されたら物理スリップ、魔法スキルで付与されたら魔法スリップになる。この動的決定のため、`attack_type` は付与モーション側（`chido_skill_motion_effect_master`、および `auto` 付与の `chido_enemy_effects_master`）が持ち、付与時に `chido_effect_slip_damage_instance.attack_type` へ複製される。ダメージ計算時には、対象の物理/魔法DEFのどちらを引くかを決めるために `instance` 側の `attack_type` を参照する（＝インスタンスに保持し続ける理由）。

**`auto` 付与（自滅）のATK（決定事項）**: `auto` 付与（`granter_entity_id = 自身`）の `SlipDamage`（「6行動で自滅する敵」等）は、その敵自身のATKをスナップショットとして用いる。6.2 で `granter_entity_id`（=自身）の与ダメージとして計上され、被弾側（=自身）のTPが蓄積される（4.4参照）。これらは意図した挙動である。

**併存インスタンスの発動順（決定事項）**: 併存する複数の `SlipDamage` インスタンスは `instance_id` 順に発動する。各インスタンスに最低1が保証されるため合計ダメージは順序に依らないが、途中で対象が戦闘不能になる場合の「とどめのインスタンス」の帰属や、被攻撃TP・報酬ゲート（6.2参照）の実効0の割り当ては `instance_id` 順で決定的になる。`instance_id` は意味を持たない列だが、決定的であるため最終タイブレークとして十分に機能する（DB設計「安定ソート」方針に合致）。

#### 重複付与と併存（決定事項）

**重複の定義**: 付与しようとしている状態変化について、**対象が既に保持している状態変化の中に、以下のすべてが一致する行が存在する**場合を「重複」とする。DBレベルでの一意制約は設けず、判定はアプリ側の責務。

| スコープ | 判定キー |
|---|---|
| `chido_battle_effect` | `entity_id` + `effect_key` + `affect_reason` + `granter_entity_id` + `grant_source_key` |
| `chido_player_effect` | `user_id` + `effect_key` + `affect_reason` + `grant_source_key`（**`granter_entity_id` を除外**） |

**`affect_reason` が判定キーに必要な理由**: `affect_reason` は `grant_source_key` が**どのテーブルの可読キーなのか**を示す型タグであり、多相的な外部キーの判別子である。可読キーの名前空間はテーブルごとに独立しているため、`skill_key = 'poison_touch'` と、将来 `affect_reason` に `equipment` が追加されたときの `equip_key = 'poison_touch'` は、`grant_source_key` の値だけでは区別できない。現時点で衝突が起きないのは `auto` 側が NULL だからにすぎない。

**`chido_player_effect` で `granter_entity_id` を除外する理由**: `granter_entity_id` は `chido_battle_participant.entity_id`、すなわち**セッションごとに発行される使い捨てGuid**である。セッションをまたぐテーブルの一意性判定に用いると、同じ敵種と戦うたびに `granter` が異なるため常に「重複ではない」と判定され、判定が機能しない。`granter_entity_id` を判定に含める意味は「複数の敵から同時に毒を受ける」＝付与者が同じ戦場に同時に存在するという構造があるからであり、永続スコープにその構造はない。同じ呪いを別の敵から受けたなら、それは同じ呪いである。列自体は履歴的参照として残るが、**一意性判定には使用しない**。

**NULL安全等価で比較すること**: `grant_source_key` は `affect_reason = auto` のとき NULL を取る。SQLでは `grant_source_key = NULL` は決して一致しないため、素直に書くと**auto付与の状態変化だけが無制限に重複する**という、テストで気づきにくいバグになる。NULL安全等価（`<=>`）を使うか、`affect_reason` で分岐して明示的に `IS NULL` を書く。

なお DBレベルの UNIQUE インデックスでは守れない。MySQL の UNIQUE は NULL を互いに異なる値として扱うため、`grant_source_key` が NULL の行は何行でも入る。アプリ側担保は消極的な選択ではなく、この判定キーでは唯一の選択肢である。

**重複時の挙動（決定事項）**: **拒否**。モーションは実行され、`accuracy_rate` の判定も行われるが、**状態変化の付与のみがスキップされる**。既存インスタンスの `remaining_actions` は変更されない（延長しない）。

- 例: 同一の敵から2行動にわたり毒を受けたとき、2回目の付与は行われない
- 例: 複数の敵がいて、その両方から毒を受けたとき、それぞれの毒は併存する（`granter_entity_id` が異なるため）

**なぜ拒否をデフォルトにするのか（決定事項）**: 拒否／リフレッシュ／スタックの選択は、「システムが唯一取りうる挙動」の選択ではなく「**デフォルト挙動**」の選択である。拒否をデフォルトに置いても、

- **リフレッシュ**は「解除 → 付与」の2モーション構成でデータ側から合成できる（後述の解除モーション参照。モーションは `motion_index` 昇順に再生されるため確実に上書きされる）
- **スタック**は付与元（`granter_entity_id` / `grant_source_key`）を変えることで得られる

の3つすべてが表現可能である。逆にリフレッシュをデフォルトにすると、一度当たった付与を「無かったこと」にする手段がないため**拒否は表現できなくなる**。実装の単純さだけでなく、表現力の観点からも拒否が正しい。

**拒否時の通知（必須要件）**: 重複により付与がスキップされた場合、**行動のレスポンスでその旨を通知する**。埋め込み（3.1参照）は共有表示であり「あなたが付与したもの」という閲覧者依存の情報を載せる手段が原理的に存在しないため、行動者への個別の返信が唯一の置き場所である。通知がなければ、プレイヤーには「スキルが不発になった」としか映らない。

**併存時の合算（決定事項）**: 判定キーが一致しない同種効果は併存する。併存時の合算は **2.3 のレイヤー内加算**に従う（`状態変化補正 = 1 + Σ effect_rate`）。ただし `SlipDamage` は補正値ではなく独立したダメージ発生源であるため合算則の対象外であり、**各インスタンスがそれぞれ発動する**（毒3つなら3回ダメージ）。「対象の行動枠の終了直後に発動する」という規定は、インスタンス単位で読めば矛盾なく成立する。

#### 状態変化解除モーション（`motion_type = 4`・決定事項）

- **解除対象**: `effect_key` 指定（`chido_skill_motion_dispel_master.effect_key`。解除サブタイプ専用の列であり、付与モーションの列の流用ではない）
- **削除範囲**: 対象が保持する**全スコープ**（`chido_battle_effect` + `chido_player_effect`）から、`effect_key` が一致する行を**すべて**削除する。`granter_entity_id` / `grant_source_key` / `affect_reason` は**参照しない**
- **対象エンティティ**: `target_rule` に従う（4.2参照）
- **成功率**: `accuracy_rate`
- **空振り**: 対象が該当の `effect_key` を1つも持っていない場合、0行削除で正常終了とする。モーションは実行され、`accuracy_rate` の判定も行われ、ターン・TP・反撃は通常どおり消費される。**空振りした場合も行動のレスポンスで通知する**（拒否の通知と同じ理由）
- **追加パラメータ**: なし

**付与と解除で判定キーが非対称である理由**: 「解毒」は毒の出所を問わない。3体の敵から受けた毒3つも、戦闘を跨いで持ち越した毒も、`effect_key` が一致する限りすべて消える。実装時に重複判定の5値を反射的に流用しないよう注意。

**スコープを分岐させない理由**: 対象が敵の場合は `chido_player_effect` に該当行が存在しない（敵の効果は `clear_on_battle_end` によらず常に `chido_battle_effect` に書かれる）ため、「対象が保持する全スコープから `effect_key` が一致する行をすべて削除する」という単一の規則でプレイヤーと敵の両方が扱える。

**解除は救済措置ではない**: 上記の不変条件により、すべての状態変化は解除がなくても必ず終わる。解除は純粋に表現力を増やすための追加である。したがって将来「解呪不可の呪い」が必要になっても破綻しない（それは `chido_effect_master` 側の列になる。11.4参照）。

**将来拡張の方向性（未設計・11.4参照）**: モーションに反応する効果（例: 攻撃モーション実行時にHPを回復する等）の拡張。11.2-8 の決定により「モーション属性」への反応は不要となり、反応の契機はモーションそのものに置く。現時点では方向性のみ。

なお、現時点でStatusEffectによる変動対象はHP・物理/魔法攻撃・物理/魔法防御に限られ、Speed/Luckは対象外（2.3参照）。ただし将来的にSpeed/Luckも対象に含める可能性があるため、対象ステータスを固定的な決め打ち設計にはしない方針とする。

## 6. 戦闘終了・セッションライフサイクル

### 6.1 `BattleEndReason`（更新）

```csharp
public enum BattleEndReason
{
    PlayerVictory,   // 敵側の生存参加者が Defeated により 0 になった
    PlayerEscaped,   // プレイヤー側の生存参加者が Escaped により 0 になった
    EnemyEscaped,    // 敵側の生存参加者が Escaped により 0 になった
    ChannelMissing,  // チャンネル消失により戦闘の継続が不可能になった
}
```

**なぜ`PlayerDefeat`が存在しないのか**: 非同期・飛び入り参加前提の戦闘は、参加者の総数が確定しない。仮に`PlayerDefeat`（参加者の戦闘不能）を終了トリガーに含めてしまうと、最初の1人が参加し、その1人がそのまま戦闘不能になっただけでセッションが終了（リセット）してしまう。これは非同期・飛び入り参加という前提と矛盾する。終了トリガーの詳細は4.3参照。

**なぜ`Escaped`を2つに分割したのか**: 逃走主体（プレイヤー／敵）によって、次の敵の抽選ロジックが異なるため（10.3参照）。かつ、参加者の状態分布からは逃走主体を事後的に導出できないため（4.3参照）。

**なぜ`Timeout`ではなく`ChannelMissing`なのか**: 非同期設計である以上、戦闘が長時間放置されること自体は許容している（誰かが後から行動すればよい）。問題になるのは「時間が経ったこと」ではなく「そもそも戦闘の場（チャンネル）が消えてシステム的に続行不可能になったこと」。したがって時間経過による強制終了ではなく、チャンネルの存否そのものを終了条件にする。

**セッション終了処理に必ず含まれる操作（決定事項）**: `end_reason` の値を問わず（`ChannelMissing` を含む）、参加していた全プレイヤーの「参加中セッション」の記録を削除する。これが漏れると、チャンネル消失時に `Defeated` だったプレイヤーが永久に他の戦闘へ参加できなくなる（1.1・4.3参照）。

### 6.2 報酬付与対象の判定（決定事項）

`PlayerVictory`で戦闘が終了した際、誰がアイテム・装備・通貨・経験値を獲得できるかを定める。**`PlayerVictory` 以外の終了理由では、いかなる参加者も報酬を得られない**（敵に十分なダメージを与えていた場合であっても、`EnemyEscaped` では報酬は発生しない）。

**大原則**: 報酬付与の対象は、`ParticipantStatus`（Active/Escaped/Defeated）によってではなく、**「セッション中に敵へ1回以上ダメージを与えたか」という実績**によって判定する。この判定は具体的には**「そのプレイヤーの台帳の累計与ダメージ（実効与ダメージの累計）が 0 より大きいか」**で行う（決定事項）。行動を1回以上行ったか（行動実績）ではなく、実際に1以上のダメージが台帳に積まれたか（結果）を基準とする。

- Escapeで離脱した参加者は、台帳累計の有無に関わらず対象外（4.3、既存ルールのまま）。
- `Defeated`（戦闘不能）は、それ自体では対象外の理由にならない。1対1のターンモデルでは被ダメージが常に自分の行動への反撃として発生するため（4.1参照）、`Defeated`になるには必ず1回以上行動している。台帳累計を基準にすることで、「行動して力及ばず倒れた参加者」を正しく対象に含めつつ、「一度も敵にダメージを与えていない参加者」を正しく除外できる。
- **とどめ以降の実効0は台帳に寄与しない（決定事項）**: `SlipDamage` の併存インスタンスは `instance_id` 順に発動し（5.4参照）、とどめ以降のインスタンス／モーションは `min(最終ダメージ, 適用直前HP)` により実効0となって台帳に0が積まれる。したがって「HP0の対象にしか関与しなかった参加者」は台帳累計0でゲートを通らず、報酬対象外になる。与ダメージ帰属・被攻撃TP（4.4参照）・本ゲートの三者が、同じ実効ダメージ（台帳計上値）を基準量とするため、この扱いは三者一貫して「効果なし」に倒れる。
- **支援特化と多対多での留意（拡張留意事項）**: 台帳は与ダメージのみを積むため、回復・状態変化・防御のみに徹して敵に一切ダメージを与えなかった参加者は累計0でゲートを通らない。現行の1対1前提では 6.2 末尾の設計方針（支援特化にも敵にダメージを与えられる選択肢を用意する）で実害はないが、多対多へ拡張した際に「支援役が報酬を得られない」設計課題として顕在化しうる。現時点での仕様変更は不要だが、留意点として記録する。
- 各参加者への報酬は、参加者間で分け合う共有プールとしてではなく、各自の行動実績・貢献度に基づき**個別に**算出される（10.2のドロップ判定が各プレイヤーごとに独立して行われるのと同じ考え方）。

#### 経験値の按分（決定事項）

経験値は本ゲームの中心的な報酬と位置づけ、各参加者の貢献度（累積与ダメージ）に応じて按分する。

**実効与ダメージ（台帳計上値）は本ドキュメントの単一の基準量である**。以下で定義する `実効与ダメージ = min(最終ダメージ, 適用直前HP)` は、経験値按分の分子（`own`）だけでなく、報酬付与ゲート（上述の「台帳累計 > 0」）と被攻撃TPの `被ダメージ`（4.4参照）も参照する共通の値である。定義が分裂しないよう、これらはすべて本定義を指す。

```
実効与ダメージ = min(パイプラインの最終ダメージ, 適用直前の現在HP)   ← 台帳に積む値（共通の基準量）
own    = そのプレイヤーがセッション中に敵参加者へ与えた実効与ダメージの累計
sumDmg = 全プレイヤー参加者の own の合計（Escaped 者の分も含む）
sumHp  = 組の全メンバーの「出現時MaxLife」の合計（状態変化補正を含まない）

分母 = max(sumDmg, sumHp)                      ← 常に正。ゼロ除算は構造的に発生しない
c    = own ÷ 分母                              ← Σc ≤ 1（通常戦闘では = 1）
t    = min(c ÷ 0.2, 1)
s    = t²                                      ← 按分率

基礎経験値 = E × Σ(組の各メンバーの exp_rate) ÷ 10000     （E = 組のレベル）
獲得経験値 = floor(基礎経験値 × s)
```

**実装（BigInteger・浮動小数点なし）**:

```
den = max(sumDmg, sumHp)
if (5 × own ≥ den)  gain = E × ΣexpRate ÷ 10000
else                gain = E × ΣexpRate × 25 × own² ÷ (10000 × den²)
```

**集計対象の定義**:

- 集計対象は**敵参加者へ与えたダメージのみ**。プレイヤーが味方に与えたダメージ（誤爆・巻き込み）は分子・分母のいずれにも含めない
- `SlipDamage` によるダメージは **`granter_entity_id`（付与者）の与ダメージとして計上する**。素直に実装すると「敵が自分自身に与えたダメージ」になり、毒付与に徹したプレイヤーが「1回以上ダメージを与えたか」ゲートすら通過できず報酬対象から完全に除外される。これは本節の方針（支援特化にも何らかの形で敵にダメージを与えられる選択肢を用意する）の否定ではなく、その方針が想定している選択肢そのものである。`chido_battle_log.actor_id` も付与者を記録する
- **`Escaped` 者の与ダメージも分母に含める**。除くと明確な悪用経路が生まれる（主力が敵を削りきってから `/escape` すれば、残った参加者の貢献率が跳ね上がり全員が満額を得る）。分母は「この敵を倒すために費やされた仕事の総量」であるべきで、後から誰が抜けたかで変動してはならない。含めることで Escape は「自分の報酬を捨てるが、他人の分母は残す」という自己完結したペナルティになり、4.3 の「安全弁」という位置づけと整合する
- セッション = 1つの組であるため、組の全メンバーへのダメージが自動的に合算される

**なぜ分母を「総ダメージ」にするのか**: 敵の回復があると最大HP基準では按分が破綻する。加えてオーバーキルでも破綻しない（最大HP基準では貢献率の合計が100%を超えうる）。

**なぜ分母に下限を置くのか**: 分母が相対値であるため、総仕事量が小さいほどわずかな貢献が100%に化ける。例えば「6行動で自滅する敵」（5.4 の auto 付与 `SlipDamage` で表現される）に1ダメージだけ入れて放置した場合、`own = 1, sumDmg = 1` で貢献率100%となり、レベル100の敵を単独撃破したのと同額が入る。`t²` の抑止曲線は `c` を入力にしているためこの経路には無力である。

**下限は通常戦闘では一切発火しない。** 敵は満タンで出現し（3.4参照）、プレイヤーがHPを0にして倒す以上、`sumDmg = 最大HP + 敵の回復量 ≥ sumHp` が常に成立する。発火するのは**プレイヤー以外の要因でHPが減った場合だけ**である。プレイヤーが半分削ったところで敵が自滅した場合は、取り分の合計が 0.5 になり「プレイヤーが実際にやった仕事の割合」がそのまま反映される。そして `sumHp > 0` は常に成立するため、**ゼロ除算は分母の定義により構造的に発生しない**（例外を弾く分岐ではなく定義として吸収される）。

出現時 MaxLife は再計算可能である。2.5 の通り敵の装備は出現時に確定しセッション中に変化しないため、`chido_battle_enemy.level` と `chido_enemy_master`（`hp_shape` / `strength_rate`）と装備から決定的に再現できる。状態変化補正は下限の定義から除外する（「出現時の」と限定する理由）。

**オーバーキルの扱い（決定事項）**: 台帳に積む与ダメージは、**実際に減少した現在HP分**（`min(最終ダメージ, 適用直前の現在HP)`）とする。5.1 が「最終ダメージしかクランプしない／下限は戦闘不能（0）」としており、現在HPは0で止まる。実際にHPを削った量を記録するのは、その挙動の素直な記録にすぎない。

生ダメージで積むと**オーバーキルが他人の取り分を破壊する**。例えば A が99ダメージ（敵HP100）を与え、B が残り1を10000ダメージの一撃で仕留めた場合、`sumDmg = 10099`、A の貢献率は 0.98% となり、99%の仕事をした A の取り分がほぼゼロになる。旧設計（分母＝最大HP）ではこの破壊は「貢献率100%クランプ」で B 側に閉じ込められていたが、分母を相対値にすると影響が他の参加者へ漏れ出す形に変質する。

**なぜ按分率を `t²`（凸曲線）にするのか**: 頭打ち20%の実体は「5倍の効率ボーナス」である。線形（`s = 5c`）を採ると、キャップ未満の全員がダメージあたりソロの5倍の経験値効率を得る。5%しか働かない参加者が基礎経験値の25%を得る一方、ソロは100%働いて100%であり、寄生に対する抑止が数学的にゼロになる（効率が貢献率に依存しないため）。

`t²` では効率が貢献率に比例して増加し、**貢献率4%が損益分岐点**になる（`s/c = 25c = 1` となる点）。すなわち「貢献率4%を境に、集団戦への参加はソロより効率が良くなる／悪くなる」。これが寄生の抑止線である。`p = 2`（整数指数）であることにより、按分計算全体が有理数演算として閉じ、`BigInteger` の経験値を扱うパイプラインに浮動小数点が一切混入しない。将来 `p` を動かす場合、損益分岐は `c* = 0.2^(p/(p-1))` で追従する（`p=3` なら 8.9%）。

| 貢献率 | 按分率（`t²`） |
|---|---|
| 1% | 0.2% |
| 4%（損益分岐） | 4.0% |
| 5% | 6.2% |
| 10%（10人均等） | 25.0% |
| 20%以上 | 100%（頭打ち） |

**5人までは全員が満額**（各自20%で頭打ちに到達）であり、6人以上から希釈が始まる、という明快な線引きになる。

**最低保証は設けない（決定事項）**: 5.1 の「最低ダメージ1を保証」に相当するものを経験値に置くと、1ダメージだけ入れた参加者に必ず1以上が入り、`t²` で作った抑止線が下限で無効化される。`floor` により獲得経験値が0になるのは正しい挙動である（ドロップ・通貨の対象判定は「1回以上ダメージ」ゲートのままなので、報酬がゼロになるわけではない）。

**組の基礎経験値はメンバーの合算である（決定事項）**: `chido_enemy_group_master` は `exp_rate` を持たず、`exp_rate` は個体（`chido_enemy_master`）側にしかない。組の全メンバーはレベルが共通（10.1参照）であるため、基礎経験値は全メンバーの `exp_rate` の合算となる。

**その帰結（設計上のレバー）**: 5.1 の分水嶺（`E ≤ L`）と `level = √exp`、および 10.1 の「撃破1回につき敵レベル+1」を組み合わせると、`E ≤ L` の維持に必要な戦場数は `N ≈ 2 ÷ (m × s)`（`m` = 組のメンバー数、`s` = 按分率）となる。

| 組のメンバー数 `m` | ソロ（`s = 1`）で必要な戦場数 |
|---|---|
| 1 | 2個（＝ちょうど均衡。実際は3個で優位） |
| 2 | 1個（**単一戦場で自走する**） |
| 3以上 | 1個で余剰 |

`N ≈ 2` が出てくるのは偶然ではない。1つの戦場をレベル `L` まで育てて得られる累積経験値は `Σ(i=1..L) i ≈ L²/2` であり、`level = √exp` が要求する `L²` のちょうど半分だからである。したがって「単一戦場では成長が敵に追いつかない」のは**メンバー1体の組に限った話**であり、組の構成は 10.4 のフィールド設計における強力なバランスレバーとなる。

**支援特化プレイヤーの扱い（決定事項・設計方針）**: Defend専任・味方支援目的のUseのみに徹するプレイヤー向けの例外的な救済ルールは設けない。「同格の雑魚敵は、プレイスタイルを問わず誰でも単独で倒せる」ことを設計思想の大原則とし、防御特化には反撃、支援特化には自己強化といった、何らかの形で敵にダメージを与えられる選択肢を、今後追加するスキル・装備側で用意する。この方針により、「敵にダメージを与えることが最も重要な貢献である」という基準を一貫させることができる。

### 6.3 `ChannelMissing` の検知方式（二層構造）

戦闘行動のたびにチャンネル存在確認を挟むのはコストが高いため、以下の二層で検知する。

1. **能動検知**: Bot側でチャンネル削除等のDiscordイベントを検知した時点で、即座に該当セッションを `Finish(ChannelMissing)` する。
2. **フェイルセーフ**: 上記の検知漏れに備え、一定時間ごとの定期検証（行動のたびではなく低頻度のバックグラウンド処理）で存在確認を行う。目的は「参加中の戦闘のチャンネルが存在しないので継続できない」状態を解消することであり、厳密なリアルタイム性は求めない。

いずれの経路であっても、6.1の「参加中セッションの記録の一括削除」を必ず伴う。あわせて、当該チャンネルの永続状態（現在フィールド・累積敵レベル・現在出現中の敵）も削除する。Discordのチャンネルは復活せずIDも再利用されないため、累積敵レベルが失われることは10.1の「減少しない」規定と矛盾しない。

## 7. 排他制御

同一の敵に複数プレイヤーがほぼ同時に攻撃するケースが実運用上頻発する前提のため、**悲観ロック**（`SELECT ... FOR UPDATE` 相当）を採用する。

### 7.1 ロックアンカー方式

ロック対象を個別テーブルごとに列挙するのではなく、**必ず行が存在する実体テーブルの1行をロックアンカーとして取得する**方式に統一する。

**なぜアンカー方式なのか**: 「行が存在しないこと」をロックで守ろうとすると（例: 「まだ戦闘に参加していない」状態を `SELECT ... FOR UPDATE` で押さえる）、InnoDBのギャップロックに依存することになる。ギャップロックは `REPEATABLE READ` でのみ機能し、`READ COMMITTED` に切り替えた瞬間、エラーも警告もなく排他が消滅する。常に行が存在するテーブルをアンカーにすれば、**トランザクション分離レベルに依存しない**。

### 7.2 正準ロック順序（決定事項）

デッドロックを構造的に排除するため、ロックの取得順序を以下に固定する。

1. **プレイヤー行**（`chido_player.user_id`／行動者本人）
2. **チャンネル行**（`chido_channel_state.channel_id`）
3. **セッション行**（`chido_battle_session.session_id`）

上位の段を飛ばすことは順序違反ではない。

| 経路 | 取得する行 |
|---|---|
| 戦闘行動 | ① → ② → ③ |
| セッション新規生成を伴う戦闘行動 | ① → ②（この配下で③を`INSERT`） |
| 装備変更 | ① → ③（②を飛ばす） |
| 次の敵の抽選・出現 | 既に②を保持しているため追加取得なし |

**チャンネル行が全戦闘行動の直列化点である。** これを保持している間は「1チャンネルにアクティブなセッションは1つ以下」が保証されるため、戦闘行動においてセッション行のロックは冗長である。セッション行が必要なのは、チャンネル行を取得しない非チャンネル起点コマンド（装備変更等）との排他のみ。

**セッション生成レースについて**: セッションはプレイヤーの最初の戦闘行為時に生成されるため、その瞬間にはロック対象のセッション行が存在しない。MySQLは「`ended_at IS NULL` の行がチャンネルごとに1つ」という部分ユニークインデックスを張れないため、DB制約でも防げない。チャンネル行（②）を先に取得することでこれを直列化する。

**包摂されるロック**: 参加者行（`chido_battle_participant`）およびプレイヤーの装備スロット（`chido_player_equipment_slot`）への明示的なロックは不要。上記アンカーに包摂される。敵の装備は出現時に確定しセッション中に変化しないため、ロック対象外である（プレイヤー側との意図的な非対称、2.5参照）。

`chido_player_effect` への書き込み（残り有効行動数の減衰、および解除モーションによる削除、5.4参照）も**チャンネル行②に包摂される**。対象が行動者本人か他の参加者かを問わない。

**アンカーが①ではなく②である理由**: `target_rule = 味方` の解除・付与モーションは**他プレイヤーの `chido_player_effect` を書き込む**が、行動者は他プレイヤーの行①を取得しない。チャンネル行②は全戦闘行動の直列化点であるため、これを保持している間はセッション参加者全員の `chido_player_effect` への書き込みが包摂される。②を飛ばす唯一の経路である装備変更（① → ③）は `chido_player_effect` を書かないため、②のみをアンカーとして安全が保たれる。1.1 の単一セッション制約により、あるプレイヤーの `chido_player_effect` を別チャンネルのセッションが同時に触ることもない。

### 7.3 直列化の副作用（承知の上での採用）

チャンネル行を先頭でロックすると、**同一セッション内の全戦闘行動が完全に直列化される**。1回の戦闘行動の処理時間 × 同時行動人数が、そのまま最後のプレイヤーの応答待ち時間になる。

Discordのインタラクション応答は3秒以内の一次応答が必須のため、ロック取得より先に `DeferAsync()` を呼び、ロック取得・計算完了後に応答編集（`ModifyOriginalResponseAsync()` 相当）で結果を返す。ロック待ちが発生したユーザーのコマンドも同様に `Defer` → `Edit` で後から応答する。この遅延応答を前提とすれば機能的な破綻はない。

行レベルの細粒度ロックによる並行度と引き換えに、ロック順序の規約遵守をアプリ側の全経路に強制する必要がなくなる（規約違反が即デッドロックに直結しない）ことを重視した判断である。

## 8. データ永続化（MySQL）

具体的なスキーマ定義は `chido-database-design.md` を正とする。本章はその要約と、本ドキュメント側の設計思想との対応を示す。

### 8.1 全体方針

| 観点 | 方針 | 理由 |
|---|---|---|
| 永続ID（実体1つ、繰り返し参照） | `BIGINT UNSIGNED`（Discordスノーフレーク） | 64bit符号なしにそのまま収まる |
| 使い捨てID（都度発行、再利用なし） | `BINARY(16)`（Guid） | 戦闘・参加者・敵出現インスタンス等、その場限りの実体 |
| 可読キー（人力編集するマスタデータ） | `VARCHAR(64)` | GUIDよりバランス調整・ログ確認・AIへの指示出しの際に扱いやすい |
| 巨大数値（`BigInteger`）全般 | `VARCHAR(100)`（10進整数文字列） | `DECIMAL` はMySqlConnectorが28〜29桁超を読めないため採用不可。DB設計ドキュメント「巨大数値の格納」参照 |
| うちSQL側で数値順のソートが必要なもの | `VARCHAR(100)` + 桁数のストアド生成列 | `(桁数, 辞書順)` が数値順に一致する。対象は `exp` と `amount` の2列のみ |
| 割合値 | permyriad（10000 = 100%） | `Ratio` 構造体と1:1対応。例外は2.2参照 |

非同期・飛び入り参加前提のため、ラウンド/フェーズ・イニシアティブ順・行動済みフラグ・座席番号によるターン制御は**意図的に持たない**（1〜4章の設計思想と整合）。プレイヤーごとの行動間隔制限（連打対策）もCore側には実装せず、必要であればDiscord側の運用（スローモード等）に委ねる。

参加者データ（`chido_battle_participant`）および敵の出現インスタンス（`chido_battle_enemy`）は戦闘終了後も物理削除しない前提（3.2参照）。

「1つ以下」という制約は、可能な限り1プレイヤー1行・1チャンネル1行というテーブル構造で裏付ける。単一セッション制約（1.1）と、1チャンネル1セッション制約（7.2）はいずれもこの形をとり、実効的な担保はアプリ側が行う。

## 9. Discordインターフェース

### 9.1 コマンド一覧（現状）

| コマンド | 状態 |
|---|---|
| `/attack [対象]` | スタブ実装のみ。対象オプション未追加 |
| `/skill [skill-name] [対象]` | スタブ実装のみ |
| `/use [item-name]` | スタブ実装のみ |
| `/escape` | スタブ実装のみ |
| `/status` | スタブ実装のみ |
| `/inventory` | スタブ実装のみ |
| `/defend` | 未実装（追加予定、4章参照） |
| `/target [対象]` | 未実装（追加予定、3.3章参照） |
| `/equip [装備]` | 未実装（追加予定、2.5章参照）。戦闘中の実行時はセッション行のロックを取得する（7.2参照） |
| 戦闘チャンネル初期化コマンド | 未実装（追加予定、10.5章参照） |

**`/status` の責務（決定事項）**: `/status` はプレイヤー単位の**永続情報**（レベル・経験値・装備・称号・**永続スコープの状態変化**）のみを扱う。現在HP・TP・戦闘スコープの状態変化といったセッション情報は、将来的に「戦闘状況表示」に特化した別コマンドが担う（今後の拡張。11.4参照）。

**なぜ分けるのか**: 3.4の通り、現在HPはセッションに属する値であり、非戦闘時には存在しない。プレイヤーの恒常的なステータスと、いま参加している戦闘の状況とは、そもそも表示されるべき文脈が異なる。

**分離の基準は「セッションに属するか否か」であって「状態変化か否か」ではない（決定事項）**: `chido_player_effect`（永続スコープの状態変化）は**戦闘外にも存在するプレイヤー単位の永続情報**であるため、`/status` の責務に含まれる。5.4 の通り永続スコープの効果は必ず有限の残り有効行動数を持つため、`[呪い] (7)` のように表示する。戦闘中でないプレイヤーが、自分に何が残り何行動効いているかを知る手段が他に存在しない。

### 9.2 ターゲット指定の形式（決定事項）

`[対象]` は **オートコンプリート付きの任意入力文字列** とする。

```
/attack [対象(文字列・任意・敵名でオートコンプリート)]
/target [対象(同上)]
```

固定の選択式オプション（enum的な選択肢）ではなく自由入力＋オートコンプリートを採用することで、同時に複数体出現しうる敵の中から柔軟に指定できるようにする狙い。`/skill` 等、対象を取る他コマンドも同じ入力パターンに揃える想定。

**`[対象]` は敵・味方の双方を受理する単一の引数である（決定事項）**: `[対象]` は引数を1つしか持たないが、解決された参加者の `entity_type` によって役割が決まる（4.2参照）。解決先が敵なら `CurrentTarget` を更新し、味方（自分を含む）なら `target_rule = 味方` のモーションの対象として供給する。したがって1スキルが敵対象モーションと味方対象モーションの両方を持つ場合でも、単一の `[対象]` で全モーションが解決可能であり、引数を2つに増やす必要はない。ただし、同名の敵が組に複数いる場合の識別・文字列マッチング規則・解決不能文字列時の挙動、および `/target` に味方が解決された場合の扱いは、コマンド層の実装前に別途決定する（未確定事項 B-12）。

## 10. 敵の出現・レベル進行・フィールドシステム

敵の撃破後に発生する一連の処理（ドロップ・レベル進行・次の敵の選出）を扱う。

### 10.1 敵レベルの進行（決定事項）

敵の**組**を撃破すると、次に出現する敵のレベルが1上昇する。組を構成するメンバーの数によらず、撃破1回につき +1 である（メンバー1体につき +1 ではない）。

このレベルは特定の戦闘セッション・敵インスタンスに属する値ではなく、**チャンネル単位で半永久的に蓄積する永続値**であり、減少することはない。初期値は `1`（10.5参照）。

組の全メンバーは、出現時点の累積敵レベルと同一のレベルを持つ。**メンバーごとのレベル差は設けない**（強さの差は種族値と強さ倍率で表現する、2.3参照）。

### 10.2 ドロップ処理とLuckステータスの関係（決定事項）

1. まず通常通り、アイテムごとの `drop_rate` でドロップ判定を行う。
2. 判定結果が「ドロップなし」だった場合のみ、Luckが1%以上であれば、Luck%の確率で「再抽選」の権利が発生する。
3. 再抽選の権利が発生した場合、同一の `drop_rate` でもう一度判定を行い、その結果（ドロップあり/なし）で最終判定を上書きする。再抽選は1度だけ行われる。
4. 複数プレイヤーが同一の敵の撃破に関与した場合、この判定（および再抽選）はプレイヤーごとに、各自のLuckを用いて独立に行われる。

Luck=0%（装備なしの初期状態）の場合、再抽選の権利は発生せず、通常の `drop_rate` のみでドロップが決まる。

敵が装着している装備がドロップする場合、その装備インスタンスをそのまま所有者移転するのではなく、内容を複製した新しいインスタンスとしてプレイヤー側に発行する。同一の敵から複数プレイヤーが報酬を受け取りうるため。

### 10.3 敵の抽選ロジック（決定事項）

**抽選の単位は「1体の敵」ではなく「敵の組」である。**

**なぜ組なのか**: レアリティ → 敵1体という抽選方式では、複数体の同時出現を明示的に表現できない。よくあるRPGのエンカウントと同様、フィールドに出現する敵の「組」を抽選対象とする。単体の敵は「メンバーが1体の組」として表現される。

以前は「複数のセグメントを持つ1体の敵」（多段階変身するボスのような表現）のために複数の敵データを使用していたが、これは組による表現に置き換わる。

**出現処理は2つの関数に分離される（決定事項）**: 「組を選ぶ」（`SelectGroup`）と「組を生成する」（`SpawnGroup`）に分ける。後者は呼び出し元・組が同一かどうかを問わず、常に同一の新規生成処理である（下記 B-9）。

**組の抽選（`DrawGroup`・2段階）**

1. レアリティを重み付きランダムで抽選する（重みはフィールドごとに個別に持つ。10.4参照）。再抽選時（下記）は1段目をスキップし、指定レアリティを直接用いる。
2. 決定したレアリティに属する**組**（現在フィールドに紐づくもの）の中から、完全ランダムで1つを抽選し、その全メンバーを出現させる。

```
DrawGroup(field, forced_rarity = NULL):
    rarity = forced_rarity ?? field のレアリティ重みで抽選（1段目）
    候補 = field に紐づく組のうち rarity が一致するもの
    if 候補が空:
        縮退を通知・記録する（3.1・下記B-10）
        候補 = 草原に紐づく組のうち rarity = Common のもの   ← フォールバック
        if 候補が空: throw（10.5 の起動時検証で正常系を塞ぐ）
    return 候補から完全ランダムに1つ
```

レアリティは `Common`/`Uncommon`/`Rare`/`Mythic`/`Hidden` の5段階で、**組が持つ**。`Hidden` はこの通常抽選の対象に一切含まれない、イベント専用のレアリティとして位置づけ、重みテーブル自体にもデータとして存在させない。

個体（`chido_enemy_master.rarity`）もレアリティを持つが、これは**表示専用**であり抽選には使用しない。

**草原 `Common` フォールバックの方向づけ（B-10・決定事項）**: 現在フィールドの該当レアリティに組が0件の場合、**草原の `Common` の組**から抽選する（レアリティは保存しない）。レアリティは報酬に有意な差を与える根拠であり、これを保存すると「フィールドAの `Mythic` 定義漏れが草原の `Mythic` 報酬を引き出す抜け道」になりうる。`Common` への降格は、マスタ不整合が常に「報酬が減る」方向にしか作用しないことを保証する（10.3 の `PlayerEscaped` 分岐と同じ向き）。草原の `Common` の組が0件なら例外を投げる（10.5 の起動時検証がこの正常系を担保する）。フォールバック時にフィールド自体は変更しない（草原から借りるのは組だけ）。抽選は 7.2 のチャンネル行ロック下で撃破を含む処理と同一トランザクションに入るため、例外はそのターン全体をロールバックし、プレイヤーにはエラーを返す（不整合なチャンネル状態を残さない最も安全な失敗）。

**組の生成（`SpawnGroup`・B-9・決定事項）**: 呼び出し元・組が同一かどうかを問わず、常に以下を行う。「前のインスタンスを引き継ぐ」経路は存在しない。

| 項目 | 値 |
|---|---|
| `entity_id` | 新規 Guid |
| レベル | 現在の累積敵レベル（組の全メンバー共通、10.1） |
| `CurrentLife` | `MaxLife`（全快） |
| 装備 | `chido_enemy_equipment_master` から再抽選 |
| 状態変化 | `chido_enemy_effects_master` の `auto` 付与を再適用 |
| `current_tp` | `chido_enemy_master.initial_tp` |
| `rotation_index` | 0 |
| `spawn_index` | 組の `member_index` を複製 |

前セッションで敵が保持していた状態変化（`chido_battle_effect`）はセッション終了時に除去されるため、再生成は常にクリーンな状態から始まる。プレイヤー側の `chido_player_effect` は戦闘の境界を参照しないため持ち越される。

**このロジックが呼ばれるタイミング（決定事項）**

| 終了理由 | 累積敵レベル | フィールド切替判定 | 組の選択 |
|---|---|---|---|
| `PlayerVictory` | **+1（先に行う）** | **行う（mod 2500）** | 切替**後**フィールドで `DrawGroup`（通常抽選） |
| `PlayerEscaped`（前組が `Common`/`Uncommon`） | 変化なし | 発火しえない | **前組と同一の `group_key`**（`DrawGroup` を経由しない） |
| `PlayerEscaped`（前組が `Rare`/`Mythic`/`Hidden`） | 変化なし | 発火しえない | `DrawGroup(現在フィールド, forced_rarity = Common)`（`Uncommon` は対象外） |
| `EnemyEscaped` | 変化なし | 発火しえない | `DrawGroup(現在フィールド, forced_rarity = Common)`（レアリティ分岐なし） |
| `ChannelMissing` | — | — | チャンネルの永続状態ごと削除（6.3参照） |

いずれの選択結果も、続けて `SpawnGroup` に渡され新規生成される。加えて、**戦闘チャンネルの初期化時**にも `DrawGroup`（通常抽選）＋ `SpawnGroup` が呼ばれる（10.5参照。ただしレベル加算・切替判定は含まない）。

**フィールド切替は `PlayerVictory` でのみ起こる（B-11・不変条件）**: フィールド切替判定（`累積敵レベル mod 2500 == 0`）は、累積敵レベルが変化する `PlayerVictory` でのみ発火しうる。他の終了理由では累積敵レベルが変化せず判定が発火する余地がない。`PlayerVictory` では「+1 → 切替判定 → 抽選」の順に処理し、切替後のフィールドの敵から抽選する。これは 10.4 の「切替専用カウンターを持たない」設計から自動的に導かれる。

**「同一の組を再出現」もインスタンスは再生成される**: `PlayerEscaped`（`Common`/`Uncommon`）では `group_key` を直接参照して `SpawnGroup` するため、HP全快・装備再抽選・状態変化の再適用が行われる（前インスタンスの引き継ぎではない）。この経路は `DrawGroup` を通らないため、フィールドへの紐づけの有無に依存せず、草原フォールバックの対象外である。

**なぜ敵の逃走は常に `Common` なのか**: プレイヤーの逃走は「レア敵から降りた」ことへのペナルティ（次はレアリティの低い敵になる）だが、敵の逃走はプレイヤーの選択の結果ではない。レアリティ分岐を適用すると、`Common` の敵に逃げられた場合に同じ敵が戻ってくることになり、逃走した敵と再戦するという不自然な状況になる。

### 10.4 フィールドシステム（決定事項・一部は今後の拡張として保留）

**一定間隔で自動的に切り替わるフィールド**を導入する。なぜなら、以前のプロトタイプにあった「戦場レベル毎にフィールドを開放し、UIで選択する」方式は、非同期・飛び入り参加のゲーム性と相性が悪いためである。

**フィールドの保持データ**:
- 名前
- 出現する敵のレアリティ抽選率（10.3の1段目。フィールド単位で個別に持つ）
- 出現する敵の**組**の集合
- このフィールドからの遷移先候補となる、他のフィールド

**切り替えタイミング**: 10.1の累積敵レベルが2500の倍数に達するたび（`累積敵レベル mod 2500 == 0`）に切り替わる。累積敵レベル自体は10.1のレベル進行とまったく同じ値であり、フィールド切り替え専用の別カウンターは存在しない。

**最初のフィールド**: 「草原」固定。DBのデフォルト値ではなくアプリ側の定数として解決する。

**永続化の範囲**: 「現在のフィールド」「累積敵レベル」は、チャンネル単位で保持する（`chido_channel_state`）。

**移動先抽選ロジック（現時点の決定事項）**: 現在のフィールドの遷移先候補リストから、**完全ランダム**で次のフィールドを抽選する。

```
NextField(current_field):
    候補 = chido_field_transition_master の current_field からの遷移先
    if 候補が空:
        縮退を通知・記録する（3.1・10.3のB-10と同一の通知規則）
        return 草原
    return 候補から完全ランダムに1つ
```

**遷移先候補が0件の場合（B-11・決定事項）**: `chido_field_transition_master` に行を持たない（行き止まりの）フィールドで `mod 2500` の切替が起きた場合、**草原へ遷移する**。現在フィールドに留まる案は採らない（次の判定機会も2500レベル後で同じく0件のため、フィールドシステムが恒久的に、しかも無言で停止する）。草原へ落とせば通常の遷移が再開され自己回復する。B-10（草原 `Common` 組フォールバック）と合わせ、「フィールド遷移・組抽選のいずれが破綻しても草原に落ちる」という単一の縮退規則になる。現在フィールドが草原でかつ候補0件なら、フォールバック先が現在地と一致するだけであり特別扱いは不要。

**意図的な行き止まりは自己ループで表現する（決定事項）**: `chido_field_transition_master` に `(草原, 草原)` のような自己参照行を置けば「そこから動かない」がデータ上の意図として明示され、縮退経路（行が無い＝不整合）と区別できる。

**今後の拡張として保留した仕様（「プレイヤーの意思を薄く反映する」案）**: チャンネル単位で、使用されたスキルのスキル属性（5.3の"見せかけ"の値）の使用回数をカウントする。次のフィールド抽選時、このカウントを属性ごとの重みとして扱い、フィールド側が持つ属性情報と照らし合わせる。具体的には「抽選された属性と同じ属性を持つフィールド」かつ「現在のフィールドからの遷移先候補」の両方を満たすフィールドの中からランダムに選出する。該当するフィールドが1つもない場合は、遷移先候補全体からのランダム抽選にフォールバックする。次のフィールドが確定するたびに、カウントはリセットされる。この仕様自体は確定しているが、実装コスト（チャンネル単位での属性使用回数という新たな集計・永続化が必要になる点）を踏まえ、**今回のスコープでは実装せず、将来のアップデート項目として保留する**。

### 10.5 戦闘チャンネルの初期化（決定事項）

「敵を倒すと次の敵が出る」という構造である以上、**最初の敵をどう出すか**が別途必要になる。専用のコマンドを新設する。

**処理順序**

```
1. チャンネルの永続状態を作成する
     現在フィールド   = 「草原」（アプリ側の定数）
     累積敵レベル     = 1
     現在のセッション = なし
   → 既に存在する場合、コマンドは失敗する

2. 現在フィールドのレアリティ抽選率でレアリティを抽選（10.3の1段目）

3. 決定したレアリティに属する組を完全ランダムで抽選（10.3の2段目）

4. 組のメンバー分だけ敵インスタンスを生成（レベル = 累積敵レベル = 1）

5. 「現在出現中の敵」として記録する
```

ステップ2〜5で用いる `DrawGroup`（通常抽選）と `SpawnGroup`（生成）は、`PlayerVictory` 時に呼ばれる次の敵の抽選・生成と**同一のロジック**である。ただし初期化では**レベル加算（+1）とフィールド切替判定は行わない**（累積敵レベルは1で固定、フィールドは草原固定）。同一なのは組の抽選と生成のみである。

**起動時（またはマスタ投入時）の検証（決定事項）**: `DrawGroup` の草原フォールバック（10.3・B-10）と `NextField` の草原フォールバック（10.4・B-11）は、いずれも草原の存在に依存する。この依存を実行時の例外だけで守ると発覚がプレイヤーの行動時点まで遅れるため、起動時に以下2点を検証する。2.3 が `exp` の初期値1（正常系）とクランプ（異常系）で採ったのと同じ、正常系を起動時検証で・異常系を例外で塞ぐ二重防御である。

1. `chido_field_master` にアプリ側定数の「草原」が存在する
2. 草原に紐づく `Common` の組が1件以上存在する

上記2点および `DrawGroup`／`NextField`／初期フィールド固定が参照する「草原」のフィールドキーは、同一のアプリ側定数を1箇所で参照する（二重管理を避ける。4.4 の TP契機・`Priority` 既定値が同じ `skill_key` 定数を共有するのと同じ形）。

**セッションはここでは生成しない**。1.1の通り、セッションはプレイヤーの最初の戦闘行為時に生成される。したがって初期化直後は「セッションに属さない、チャンネルに出現中の敵」が存在する状態になる。この状態は `PlayerVictory` 後に次の組が出現してから誰も行動していない期間にも同様に発生する。

**冪等性**: 初期化コマンドは「既にあるものを消去して作り直す」機能を伴わない。既に初期化済みのチャンネルで再実行された場合、コマンドは失敗する。

**累積敵レベルの初期値が `1` である理由**: 2.3の `基礎ステータス = レベル × Scale × Shape` において、レベルが `0` だと全ステータスが `0` になり計算式が破綻するため。敵レベルは累積敵レベルから直接与えられ、初期値1・減少なし（10.1参照）であるため常に1以上が保証される（プレイヤー側の `level = max(1, floor(√exp))` のクランプに相当する保証を、敵側は初期値と単調増加で担保する）。

**実行権限**: 現時点では制限を設けない（誰でも実行可能）。問題が発生した段階で改めて検討する。

**チャンネル消失時**: `ChannelMissing` によるセッション終了時、チャンネルの永続状態と現在出現中の敵の記録を削除する。Discordのチャンネルは復活せずIDも再利用されないため、再初期化の必要は生じない（6.3参照）。

3. **一時的な属性付与のインスタンス側テーブルの要否**: 付与属性がマスタ固定であればマスタのみで完結し、行動不能（`DisableMove`）と同じ扱いになる（5.4参照）
4. **戦闘ログの粒度**: 1行=1ターンか、1行=1モーションか（1スキルが複数モーションを持つため）。動作には影響せず、11.2-1 の集計方法との整合の問題
5. *(解消)* 敵が「味方」対象のスキルを使う場合の対象解決規則 — **決定**。`chido_enemy_master.ally_target_rule`（種族単位）で解決し、現行は完全ランダム(0)／自分以外からランダム(1)／最小HP割合(24)の3規則を実装、他は予約値として将来拡張とする。候補集合は自分を含む（4.2参照）
6. *(解消)* `target_rule = 味方` に自分自身を含むか、`[対象]` 省略時の既定 — **決定**。「味方」は自分自身を含み、`[対象]` 省略時は行動者自身に解決する。`target_rule = 自分自身` は「指定があっても対象は変わらない」より強い規則として区別される（4.2参照）
7. *(解消)* `[対象]` に `Escaped` / `Defeated` を指定できるか — **決定**。`Escaped` は候補集合に存在せず指定不可、`Defeated` は指定可だが常に拒否（将来の蘇生スキルのための布石として非対称なメッセージを与える）。いずれも行動の不成立でありターン・TP・反撃・減衰を生じない（4.2参照）
8. *(解消)* スキルモーションマスタのサブタイプ化：`elements` の配置 — **決定**。属性は攻撃モーションのみが持ち、`chido_skill_motion_attack_master.elements` に置く。攻撃と回復のサブタイプを分割し、回復・付与・解除・離脱は属性を持たない（4.2・5.3・11.4-4 参照）
9. *(解消)* スキルモーションマスタのサブタイプ化：テーブル名 — **決定**。親を `chido_skill_motion_master`（単数形）に改称。攻撃は `chido_skill_motion_attack_master`、回復は `chido_skill_motion_heal_master`。付与 `effect`・解除 `dispel` は据え置き。「HP干渉」の語彙問題は攻撃・回復の分割で消失

**11.2-10 は本改訂で 11.3-1 から格上げした。** Attack/Defend の `skill_key` が、習得管理除外・TP契機（4.4）・`Priority` 既定値（4.1）の3者から参照される共通の定数となったため、単なる表現様式の差ではなく実装上の集約点になった。

10. **Attack・Defend の `skill_key` の集約方式**（旧 11.3-1 から格上げ）: Attack/Defend は習得手続きなしに全プレイヤーが常時使用でき、`chido_player_skill` の管理対象外とする（除外自体は確定）。加えて、TP+100の契機判定（4.4：Attack/Defendモーションの再生）と `Priority` 既定値の付与（4.1：Defendに正値）も、この2つの `skill_key` を参照する。したがって「スキルマスタにフラグ列を設ける」か「アプリ側の定数で `skill_key` を決め打ちする」かは単なる様式差ではなく、3つの参照点が同じ1箇所を指すための集約設計になる。アプリ側の定数として1箇所に集約するのが素直
11. *(解消)* 命中判定の道連れ（`accuracy_gate_group`）— **決定**。`chido_skill_motion_master` に `accuracy_gate_group SMALLINT UNSIGNED NULL` を追加。同一 `skill_key` 内で同値の行が1グループを成し、`motion_index` 最小の先頭が効果適用に到達しなければ他メンバーをスキップ、到達すれば他メンバーはそれぞれ自身の `accuracy_rate` を独立抽選する。NULL は単独判定（現行挙動）で後方互換。A-6 の検討中に「攻撃命中 → n% で状態変化付与」を表現する手段として新規に起こした項目（4.2参照）

### 11.3 任意

好みやスタイルに依存し、やってもやらなくてもよい項目。

**現時点でなし。** 旧 11.3-1（Attack・Defend の除外方式）は、TP契機・`Priority` 既定値の参照点となったことで動作差が生じ、11.2-10 へ格上げした。

### 11.4 将来検討

今後の拡張（アップデート）方針として先送りし、優先度の枠組みから除外する項目。すぐに実装するわけではないが、「今後これをする予定がある」ことを明示しておくことで、機能追加時の競合や実装の複雑化を避けるねらいがある。

1. **装備限定スキルの参照経路**: 装備側から動的に参照する方針までは確定。1装備に複数スキルを許容するか単一のスキルに限定するかによってテーブル設計が変わる。装備限定スキル自体の実装とあわせて将来対応とする（2.5参照）
2. *(欠番)* 永続スコープの状態変化への持続の適用可否 — 5.4 で確定（**適用する**。永続スコープの効果は必ず有限の `remaining_actions` を持つ）
3. **TPシステムの拡張**: 固定蓄積量（Attack+100/Defend+100/被攻撃比率）への%補正、または新規蓄積トリガー（毎ターン蓄積等）の追加（4.4参照）
4. **モーションに反応する効果の拡張**: 例として攻撃モーション実行時にHPを回復する等（5.3/5.4参照）。当初は「モーション属性に反応する効果」として構想し 11.2-8（`elements` の配置）の親項目であったが、11.2-8 の決定（属性は攻撃モーションのみが持つ）に伴い方針を変更し、**「モーション属性」への反応は不要**とした。反応の契機はモーションそのもの（種別・実行の有無等）に置く形で残す。変更の詳細は将来設計する
5. **フィールド移動先抽選における「プレイヤーの意思反映」ロジック**: チャンネル単位のスキル属性使用カウントに基づく重み付き抽選。仕様は10.4で確定済み、実装は保留
6. **状態変化によるSpeed/Luckへの影響**: 現時点では無し。ただし将来解禁する可能性があるため、既存効果（HP/攻撃/防御）への決め打ち設計にはしない方針（2.3/5.4参照）
7. **「戦闘状況表示」コマンドの新設**: 現在HP・TP・状態変化などのセッション情報の表示。`/status` から分離する（9.1参照）。3.1 の文字数予算から、上限は **20参加者 × 5種類**。これを超える件数を表示したい場合は**ページングが必須**（Discord の6000文字制限はメッセージ単位の合計であり、埋め込みの分割では回避できない）。また、埋め込みに載せられない閲覧者依存の情報（「どの毒が自分の付与したものか」等）の受け皿でもある
8. **装備の個体差・強化**: 装備インスタンスがGUIDを持つため、将来的に個体差用のサブテーブルを追加できる余地を残している（2.5参照）
9. **戦闘チャンネル初期化コマンドの実行権限**: 現在は無制限。問題が発生した段階で検討する（10.5参照）
10. **「解除不可の状態変化」**: 将来必要になった場合、それはモーション側ではなく `chido_effect_master` 側の列（例: `dispellable`）になる。「この効果は解除の対象にならない」は効果の性質であって、解除する側の性質ではないため。5.4 の不変条件（すべての状態変化は有限の行動数か戦闘の終了によって必ず終わる）があるため、解除不可の効果があっても暴走しない
11. **スキルモーションマスタのサブタイプ化：読み取り用 VIEW**: 親＋子の LEFT JOIN で現行と同一の平坦な形が得られるが、これを VIEW として定義するか、C#側で JOIN を書くか。`CREATE VIEW` は既存テーブルに触れず、いつ追加・削除しても何も壊れないため、実際にデータを手入力して煩雑だと感じた時点で追加すればよい

### 11.5 未確定事項ではない検討項目

**スキルモーションマスタのサブタイプ化のマイグレーション方式**: これは設計上の未確定事項ではなく事実確認である。DBの構築自体がまだ行われていないため、テーブル定義を書き直す以外の作業は生じない。リファクタ実行時のチェック項目として扱う。

### 11.6 初回抽出（実装者視点の曖昧さ）からの未着手項目

ドキュメント全体を実装者視点で走査し、記述から複数パターンの実装が考えられる箇所を抽出した。うち A-1／A-3／A-4／A-5／B-2 系（行動順の最終タイブレーク・スリップダメージ・レベル算出・適用フェーズと丸め・防御とパイプライン）に加え、本改訂で **A-2／A-6／A-7／A-8／A-9／B-9／B-11（必須7件すべて）** および A-10／B-10 が確定・反映済み。以下は分類ごとに整理する（節番号11.1〜11.3の基準と同一）。ID は抽出時のものを維持する。

#### 必須（決定を欠くと実装できない、または戦闘中に到達しうる挙動が未定義になる）

**本改訂により、必須7件すべてを解消した。** 以下は各項の決定内容と反映先である。

- *(解消)* **A-2**: 先攻の複数モーション途中で対象が戦闘不能・離脱した場合、以降のモーションは対象状態判定（4.2 ステップ3）に従う。対象が `Active` なら再生、`Defeated`／`Escaped` ならそのモーションのみスキップ。行動者は `Active` のままなので末尾の自分自身対象モーションは再生される（4.2参照）。
- *(解消)* **A-6**: 命中判定を外したモーションはスキップし、パイプラインに入らない（ダメージ0を通さない）。後続モーションは止めない。TP契機は「効果適用への到達」で決まるため命中失敗では発火しない。反撃は通常通り発生し減衰も起きる。Attack/Defend は `accuracy_rate = 10000` 固定の運用制約を置く（4.2・4.4・5.1参照）。
- *(解消)* **A-7**: `disable_rate` を毎回抽選。(b)ターン消費・(c)TP蓄積・(d)反撃・(e)減衰はいずれも成否によらず常に行われる（ただし (c) の +100 はモーション再生を契機とするため行動不能では発生しない）。成立時にスキップされるのはモーション再生のみ。f〜j の詳細（併存合成・`require_tp` 不消費・`rotation_index` 前進・判定タイミング・`SlipDamage` 発動）も確定（5.4参照）。
- *(解消)* **A-8**: 減衰対象はターン開始時に固定される「行動者＋反撃者（`CurrentTarget`）」の2エンティティ（関与者集合）。行動キャンセル・撃破・行動不能は集合を変えない。`Use` 等で受動的に影響を受けた第三者は減衰しない。行動が不成立ならターンが開かず減衰も起きない（5.4参照）。
- *(解消)* **A-9**: 初回既定・自動失効後の再選定を区別しない単一の導出関数（格納値が `Active` ならそれ、さもなくば `Active` な `display_order` 最小の敵）。後段に落ちた結果は書き戻す。候補0件は例外（3.3参照）。
- *(解消)* **B-9**: 「`Common` から再抽選」はレアリティ抽選をスキップし `Common` 内から完全ランダム。「同一の組を再出現」も含め、組の生成は常に新規（HP全快・装備再抽選・状態変化再適用）で引き継ぎ経路はない（10.3参照）。
- *(解消)* **B-11**: フィールド切替判定は `PlayerVictory` の「+1」の後に行い、切替後フィールドから抽選する。遷移先候補0件は草原へフォールバック、意図的な行き止まりは自己ループで表現（10.3・10.4参照）。

- *(解消)* **A-10**: 敵側の `CurrentTarget` は不要と確定。A-9 の導出関数は `entity_type = Enemy` の参加者を返すもので、プレイヤーからの解決にのみ用いる。敵の `target_rule = 敵` は「そのターンの行動者」に自明に解決されるため、敵は `current_target_id` を持たない（DB 4番の「Enemy: 常にNULL」に寄せる。記述統一のみで解消）。敵の味方対象解決は `ally_target_rule`（11.2-5）が別系統で担う。
